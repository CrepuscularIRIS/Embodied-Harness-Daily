===ABSTRACT===
Simulated manipulation benchmarks measure policy performance using hand-written success checkers that label each episode as a success or failure. Passing an expert demonstration shows that a checker accepts one way of completing the task. Learned policies, however, may stop after partial progress or complete the task in a different way. A checker may then accept an incomplete execution (phantom success) or reject an execution that satisfies the instruction (silent failure). In this paper, we introduce SimAudit, an LLM-based pipeline that audits success checkers against task instructions. SimAudit analyzes the instruction and checker code to identify scenarios where the two may disagree, recreates those scenarios in simulation, and runs the original checker. Multi-view renderings are then used to verify whether the observed behavior satisfies the instruction. Across RoboTwin 2.0, RoboCasa365, and RoboDojo, 183 simulated test cases produced the predicted checker verdict. Visual verification and deduplication yielded 61 distinct defects across 49 tasks, including 40 phantom successes and 21 silent failures. Most defects in RoboCasa365 accepted incomplete executions, most in RoboDojo rejected valid executions, and both error types were common in RoboTwin 2.0. These findings suggest that validating success checkers requires testing both incomplete executions and valid alternatives to expert demonstrations, and motivate more rigorous evaluation protocols for future benchmarks.

===INTRO===

Task success rate is the primary metric for comparing robot manipulation policies in simulation. Each episode is scored by a success checker , a hand-written rule that uses simulator state to determine whether the robot completed the task specified by the instruction. Evaluating generalist manipulation models, including vision-language-action models ( Brohan et al., 2023 ; Kim et al., 2024 ; Black et al., 2026 ; Song et al., 2026b ; Lu et al., 2026b ) and world action models ( Li et al., 2025 ; Bi et al., 2025 ; Lin et al., 2026 ) , on physical robots is costly and difficult to reproduce across laboratories ( Zhou et al., 2025 ; Song et al., 2026a ) . Recent simulated benchmarks such as RoboTwin 2.0 ( Chen et al., 2025 ) , RoboCasa365 ( Nasiriany et al., 2026 ) , and RoboDojo ( Chen et al., 2026b ) therefore play a central role in model evaluation. They aggregate checker verdicts into the success rates used to rank policies. Prior work has shown that these rates can be affected by memorization of training configurations ( Zhou et al., 2026b ; Fei et al., 2025 ) , task shortcuts and overfitting to fixed test sets ( Jiang et al., 2026 ) , and artifacts in the physics engine ( Zhou et al., 2026a ) . The reliability of the success checkers that produce these rates has received less attention. This raises a basic question: do checker verdicts accurately reflect whether a robot’s execution satisfies the task instruction? Expert demonstrations can establish that a success checker accepts a reference execution. RoboTwin 2.0 ( Chen et al., 2025 ) , for example, retains an evaluation seed only if the scripted expert passes the checker on that seed. A learned policy can reach states outside those covered by the demonstrations by stopping before the task is complete or by completing it in a different way. Figure 1 illustrates two errors that can arise in these states. The first task illustrates a phantom success . The checker reports success when the robot lifts the bottle 3 cm off the table without shaking it. A phantom success occurs when the checker marks an execution as successful even though it does not satisfy the instruction. The second task illustrates a silent failure . The robot picks up one bottle with each arm as instructed, but the checker reports failure because it additionally requires both bottles to be at the centre of the table. A silent failure occurs when the checker marks an execution as failed even though it satisfies the instruction. Validation with scripted experts can miss checker errors because expert trajectories may never expose discrepancies between the instruction and the conditions the checker tests. To uncover these errors, we introduce SimAudit, an LLM-based pipeline that audits success checkers on states that scripted experts never reach. Given a task instruction and its checker code, an LLM agent compares the requirements in the instruction with the conditions tested by the checker. It uses discrepancies between the two to propose states that the checker may misclassify. For each proposed state, the agent predicts from the code whether the checker will return success or failure. The agent then constructs the state in simulation, using robot motion governed by simulated physics wherever possible. The pipeline runs the unmodified checker on the resulting state and renders the scene from multiple camera views. A candidate is retained only if the rendered views establish that the execution’s outcome under the instruction differs from the checker verdict. Across 142 tasks in the three benchmarks, the agent proposed 568 candidate states. The actual checker verdict matched the agent’s prediction in 183 cases. Visual verification and deduplication yielded 61 distinct checker defects. We identify 61 defects across 49 tasks in RoboTwin 2.0, RoboCasa365, and RoboDojo, including 40 phantom successes and 21 silent failures. RoboCasa365 has 17 phantom successes and one silent failure, while RoboDojo has three phantom successes and nine silent failures. Both types are common in RoboTwin 2.0, with 20 phantom successes and 11 silent failures. These patterns reflect the conditions each benchmark’s checkers enforce. RoboCasa365 checkers often omit conditions required by the instruction, allowing incomplete executions to pass. RoboDojo checkers often impose conditions beyond those in the instruction, causing executions that satisfy the instruction to fail. These errors can inflate or depress reported success rates. To measure their effect on released policies, we repair the defects identified by SimAudit and score the same policy rollouts with the original and repaired checkers. We count a verdict change whenever the two checkers disagree on an episode. Our contributions are threefold. ## 3 Auditing Success Checkers
3.1 Phantom success and silent failure A task comes with an instruction and a checker, a function of the simulator state that returns success or failure. The benchmark ends the episode at the first state on which the checker returns success and records a success; if none occurs before the time limit, it records a failure. A phantom success is credit for an execution that does not fulfil the instruction: the robot does part of the task, does something else, or only passes through the accepted state. A silent failure is credit withheld from an execution that fulfils it: the robot completes the task by a route, or to an end state, that the instruction allows and the checker does not. A person who reads the instruction and looks at the scene decides whether it is fulfilled. Both are judged on the state at which the benchmark gives its verdict; what the robot would have done after the episode ends does not count. A checker defect is a flaw in a checker together with a state that shows it. We count a defect when three conditions hold. (i) The state is rendered, and the disagreement between the checker and the person is clear from the pictures. (ii) The checker value is read from the unmodified benchmark code at that state. (iii) The state is reachable: it is produced by motions of the robot or of the scripted expert under physics, or it is a pose in which an object rests after it is released and left to settle. A state that exists only while an object is teleported into place, such as an object floating without support or two objects interpenetrating, shows what the code computes but is not counted. Each defect is counted once: several states that show the same flaw in the same task are one defect. 3.2 SimAudit: read, guess, stage, review SimAudit is an automated pipeline that audits a benchmark’s success checkers against its task instructions. Given a task, it constructs targeted test executions, records the original checker’s verdicts, and uses rendered evidence to verify potential mismatches. We illustrate the pipeline in Fig. 2 . The framework could be divided into four stage as following. Read. SimAudit starts by establishing what the task asks for and what the checker tests. An LLM agent receives the instruction templates given to the policy, the source of the task with its success checker and every helper it calls, the benchmark’s evaluation loop, and the scripted expert when the benchmark provides one. The agent first writes, from the instruction alone, what has to be true of the scene for the task to count as done. It then writes, from the code alone, what the checker accepts. We ask for the two descriptions separately so that the agent’s reading of the task is not taken from the checker’s conditions. As shown in Figure 2 A, the instruction of “place object stand” asks for the object to be placed on the stand, and the checker accepts any state in which the object is within 3 cm of the stand horizontally and both gripper commands are open; it tests neither the height of the object nor its contact with the stand. Guess. Given the two descriptions, the agent proposes up to four hypotheses for the task. Each hypothesis names a state, the verdict the checker will give on it, and the opposite judgement of a person who reads the instruction, together with the line of code responsible. The agent also states how the state can be built and which measurement would confirm the hypothesis, so that the next stage has a prediction to test. As shown in Figure 2 B, the agent writes four hypotheses for “place object stand”. The object is held above the stand and never set down, the open command is sent while the fingers are still closed, the object is set down off-centre but within the tolerance, or the stand is pushed along with the object.
