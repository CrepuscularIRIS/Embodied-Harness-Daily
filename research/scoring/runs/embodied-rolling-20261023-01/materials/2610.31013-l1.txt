# Multi-Tool Selection for Robotic Systems: Comparing Semantic Retrieval and LLM

## Abstract
Natural-language interfaces allow users to command robotic systems without interacting directly with mission planners or robotics middleware. Their reliable use depends on robot tool routing, defined here as the selection of the smallest complete subset of predefined executable capabilities required to satisfy a request. This task is particularly difficult for compound instructions, where incomplete selection may omit necessary sensing or monitoring capabilities, while excessive selection may expose irrelevant tools. We compare four routing strategies: three progressively refined ChromaDB-based methods - fixed-threshold retrieval, relative-distance retrieval, and clause-aware aggregated retrieval - and a cloud-hosted 120-billion-parameter language-model baseline. The methods are evaluated on 164 manually annotated prompts organised into three complexity levels, from direct single-tool requests to compound requests requiring at least three tools. Using exact-match accuracy, completeness, precision, a completeness-weighted composite score, and routing latency, CDB-v3 achieves the best macro-average score among the retrieval-only methods, with 0.7822, compared with 0.8869 for the large-model baseline. Although the LLM provides higher routing quality, CDB-v3 exhibits substantially lower latency and can be deployed locally without requiring cloud connectivity. These results identify a quality-latency trade-off between direct large-model selection and clause-aware semantic retrieval for privacy-sensitive, connectivity-constrained, and resource-constrained robotic systems.

## 1 Introduction
Natural-language interfaces are becoming an attractive way to interact with robotic systems. Instead of invoking commands through mission planners, terminals, or custom graphical interfaces, users can express requests directly in natural language, such as “land the drone”, “start mapping the area”, or “report the current battery level”. Large language models (LLMs) make such interfaces increasingly practical, but a critical challenge remains: mapping a user request to the correct robot capability or set of capabilities. In robotics, capability selection is not merely a usability problem. A routing error may activate an incorrect process, produce misleading information, or issue an unintended command to the robot. As the number of available robot functions grows, reliable intent-to-capability matching becomes a fundamental requirement for safe and effective natural-language control. Traditionally, this decision logic is encoded through behaviour trees, state machines, launch configurations, or manually designed if–then rules that determine which robot capability should be activated under each condition. These approaches remain effective for predefined and well-structured workflows, but they become increasingly difficult to design, extend, and maintain as the number of capabilities, mission types, operating conditions, and possible user requests grows. Conversational interfaces shift part of this burden from handcrafted decision logic to runtime capability selection, making the routing layer a critical component of the overall system. This challenge is particularly relevant in ROS-based systems, where a single robot or fleet may expose dozens of processes for navigation, mapping, monitoring, mission execution, telemetry collection, payload operation, and system management. A request may require one capability or a coordinated set of capabilities. For example, the instruction “monitor the battery and land when it drops below 25%” requires both a telemetry capability and an actuation capability. The routing layer must therefore determine not only which capabilities are semantically relevant, but also whether several tools must be selected to satisfy all parts of the request. Large LLMs can perform this selection directly by receiving the complete tool catalog and reasoning over the user request. However, dependence on a cloud-hosted model may be impractical in robotic deployments with intermittent connectivity, limited bandwidth, high communication latency, or strict confidentiality and data-sovereignty requirements. Robot telemetry, mission information, maps, and operational commands may be unsuitable for transmission to external infrastructure. Even when a large model can be deployed locally, its memory, computational, energy, and latency requirements may exceed the resources available at the robotic edge. These constraints motivate lighter routing mechanisms that can execute locally, while preserving as much selection quality as possible. This paper studies tool routing as a bounded multi-label selection problem. The router cannot invent commands or generate arbitrary executable code. Instead, it must select a subset from a fixed allowlisted catalog of 42 robot tools. We compare four implementations of this routing function: CDBv1, which uses a fixed semantic-distance threshold; CDBv2, which uses a threshold relative to the nearest result; CDBv3, which decomposes compound prompts into intent-like clauses and aggregates their retrieval results; and a cloud-hosted 120-billion-parameter LLM that performs direct selection from the complete catalog. The evaluation uses 164 manually annotated requests divided into three complexity levels: 43 direct single-tool requests, 52 consequential requests requiring exactly two tools, and 69 compound requests requiring three or more tools. All routers are evaluated against the same ground-truth assignments using exact-match accuracy, completeness, precision, a completeness-weighted composite score, and routing latency. The main contributions of this work are the formalisation of robotic tool routing as bounded multi-label capability selection, an empirical comparison of fixed-threshold, relative-distance, and clause-aware semantic retrieval under the same tool catalogue and prompt dataset, and a direct comparison between the strongest retrieval-only method and a large cloud-hosted LLM, exposing the resulting trade-off between routing quality and latency. The results show that CDBv3 is the strongest retrieval-only strategy. Its macro-average composite score is 0.7822 , compared with 0.5863 for CDBv2 and 0.3330 for CDBv1. The 120B LLM achieves a higher score of 0.8869 , but CDBv3 provides substantially lower routing latency and does not require cloud connectivity. ## 3 Problem Formulation
Let \mathcal{T}=\{t_{1},t_{2},\ldots,t_{n}\} (1) denote the finite catalog of n tools available to the robotic system. Each tool t_{i}\in\mathcal{T} is identified by a unique name and is associated with a natural-language summary, a detailed description, an executable interface, and usage metadata. The executable interface is defined in advance; the router is not allowed to create new tools or arbitrary commands. An input request x\in\mathcal{X} is a natural-language prompt submitted by a user and may express one or more intents related to the robot’s capabilities. A tool router performs multi-label selection: it may return no tool, one tool, or several tools. The routing function is therefore defined as f:\mathcal{X}\rightarrow 2^{\mathcal{T}}, (2) where 2^{\mathcal{T}} denotes the power set of the tool catalog. For a request x , let Y(x)\subseteq\mathcal{T} denote the ground-truth set of required tools and let \widehat{Y}(x)=f(x) (3) denote the set predicted by the router. For example, the request ‘‘Tell me the battery level.’’ requires only the battery-monitoring tool, yielding Y(x)=\{\texttt{battery}\} . In contrast, the request ‘‘If the battery is below 20% or the wind exceeds 10 m/s, land.’’ requires two observation tools and one actuation tool: Y(x)=\{\texttt{battery},\texttt{wind\_speed},\texttt{land}\}. (4) Returning only \widehat{Y}(x)=\{\texttt{land}\} is incomplete because the system cannot evaluate either triggering condition. Returning \widehat{Y}(x)=\{\texttt{battery},\texttt{wind\_speed},\texttt{land},\linebreak\texttt{whereami}\} is complete, but includes one unnecessary tool. Router performance is evaluated using three request-level measures: exact-match accuracy A(x) , completeness C(x) , and precision P(x) . Exact-match accuracy is one only when the predicted and reference sets are identical: A(x)=\mathds{1}\left[\widehat{Y}(x)=Y(x)\right]. (5) Completeness is a binary request-level measure indicating whether all required tools are present, regardless of additional selections: C(x)=\mathds{1}\left[Y(x)\subseteq\widehat{Y}(x)\right].
