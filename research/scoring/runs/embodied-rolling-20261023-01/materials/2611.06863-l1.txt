# Rethinking Self-Repair in Code-as-Policy Agents: What Drives Retry Success?

## Abstract
Code-as-policy agents often use execution feedback to retry failed programs. Additional sampling and task guidance can also improve success, leaving the contribution of failure-specific feedback unclear. We study this question in simulated robot manipulation. A fixed lookup selects feedback templates using failure labels and the API variant. A frozen code model generates a fresh program after each scene reset. On the same 252 initial failures, Qwen2.5-Coder-7B recovers 85.3% within five retries, compared with 68.3% for resampling with the same retry cap. The advantage persists under fixed total-token budgets. Feedback from other episodes and fixed task guidance yield similar recovery point estimates, with no detected benefit from matching the coarse failure label. In a separate study, a fixed guided prompt used from the first attempt achieves an observed overall success rate similar to that of template-based feedback. Template-based feedback also lowers recovery on a nut-insertion task requiring a rim grasp, consistent with an incompatible center-grasp instruction. Evaluations of robot self-repair should include resampling, mismatched feedback, and concise, task-compatible static guidance as baselines.

## 1 Introduction
Code-as-policy agents translate language instructions into executable robot programs [ 1 ] . Their failures often follow clear patterns: a program may skip the grasp, release an object after lifting, or place it away from the target. A common response is iterative self-reflection. The model reads its failed program and execution trace, writes a critique, and tries again [ 2 , 3 , 4 ] . Retry success can reflect additional sampling, concise task instructions, feedback about the current failure, or editing the previous program. We ask whether feedback after failure improves recovery over guidance available from the first attempt. We study this question with frozen Qwen2.5-Coder-3B/7B models in a reset-and-retry setting. Each retry starts from the original scene. Our main conditions generate a fresh program with the failed program omitted from the prompt. We use template-based feedback to study which information improves retry success. A fixed lookup selects instructions using the failure label and API variant, such as “MUST grasp the object before lifting.” We call this condition Compiled . The lookup lets us replace matched feedback with another episode’s feedback, hold the guidance fixed, or remove it while keeping the retry loop unchanged (Figure 1 ). Separate editing conditions expose the previous program and request a revision. All conditions restart the original scene. We do not test recovery from the physical state left by failure. Compiled recovers 85.3% of the 252 initial failures within five retries, compared with 68.3% for resampling with the same retry cap. The gain persists under fixed total-token budgets. Feedback from other episodes and one fixed template per task produce similar point estimates. We detect no benefit from matching the coarse failure label to the current episode. The confidence intervals still allow differences between conditions. In a separate study, a fixed guided prompt used from the first attempt achieves an observed overall success rate similar to Compiled’s, with fewer tokens per solved episode. That comparison changes initial guidance and the generation instruction together. Their individual contributions remain unresolved. We compare feedback content and program-generation strategies under matched retry budgets to test how additional sampling, reusable task guidance, and failure-label matching affect recovery. Evaluations of robot self-repair should include static guidance as a baseline for adaptive feedback.

## 3 Methods
3.1 Experimental Setup We evaluate frozen code models in robosuite simulation with a Panda arm [ 23 , 24 ] . Models receive state information and generate Python programs using a documented robot API, without images. The primary evaluation uses Qwen2.5-Coder-7B-Instruct [ 25 ] with the primitive API on cube lifting and stacking. An episode comprises an initial program execution for a task and scene, followed by any retries under one method. The initial execution is attempt 0 . After an initial failure, the model is allowed up to five retries . Before each retry, the simulator resets to the original scene. Each retry produces a complete program, either generated from scratch or revised from the previous program. We use 252 initial failures for evaluation and 40 for development. The sets contain distinct initial programs, identified by their hashes. The evaluation covers 159 combinations of task, API variant, and scene, including 24 also used in development. All methods are evaluated on the same stored initial failures. The end-to-end studies pair methods by scene seed. Conditional recovery@ k is the fraction of attempt-0 failures solved within k retries. This metric measures sequential retries and differs from pass@ k estimated from independent samples. For end-to-end studies, initial success is success on attempt 0 and overall success@6 is success in any of the six allowed executions. An attempt is valid if its program compiles, uses only documented API functions, and finishes before timeout. The generalization study includes Qwen2.5-Coder-3B/7B and two additional pick-and-place tasks. We combine results across seven settings that meet the predefined eligibility criteria. Separate studies examine API variants with fewer high-level helper functions, Qwen2.5-Coder-32B, and DeepSeek-Coder-6.7B [ 26 ] . Further details of the software, tasks, evaluation sets, and metrics are provided in Appendix A . 3.2 Template-Based Feedback After an unsuccessful execution, a rule-based labeler assigns one primary label from a 14-label taxonomy. Compiled maps this label and the API variant to a fixed feedback template containing a diagnosis and short MUST/NEVER instructions (Table 1 ). This lookup requires no additional model call. The instructions guide code generation without imposing execution-time checks. Compiled accumulates feedback from the initial failure and subsequent failed retries, retaining the labels and attempt indices. The feedback block presents the newest feedback first, omits duplicate instruction lines, and respects the feedback-length limit. The generation prompt contains the task, API documentation, and accumulated feedback, with the previous program omitted. An example from the earlier study shows an initial failure followed by a successful fresh retry (Figure 2 a). Resample repeats the base retry prompt without feedback. Other-Episode Feedback replaces the current episode’s feedback with feedback from other failures, matched by task, API variant, and initial task-progress bin. The primary matching control, Different-Label Feedback , selects individual feedback records from other episodes of the same task, preferring the same initial task-progress bin and requiring a different failure label whenever available. Both add feedback as the evaluated episode accumulates failures and use the same feedback-length limit. These controls test the value of matching the coarse failure label while retaining useful task information. The matching and fallback rules are specified in Appendix B.3 . We select a fixed template for each task from the development data, choosing the most frequent failure label with task-compatible guidance. Fixed Task Template reuses this template across retries after the initial failure. Static-from-Start uses the complete Fixed Task Template retry prompt from attempt 0, changing both the initial generation instruction and the presence of guidance. Direct+Compiled shows the failed program and requests an edit, jointly changing code exposure and the generation instruction. Reflection uses an extra model call to critique the failed program and execution log. Its generation call receives the accumulated critiques and omits the previous code.
