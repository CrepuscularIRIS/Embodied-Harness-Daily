===ABSTRACT===
Coding agents built to repair software now write, test, and repair programs for robots, laboratories, and industrial controllers. Unlike in software engineering, no test suite comes with the code. Whether a program works must be established by running it on a robot, in a physics simulator, or through the policies it helps to train, and such evidence is costly to obtain and can itself be wrong. As these agents take on more physical tasks, how their programs are judged matters as much as how they are written. This paper examines this emerging area, agentic intelligence for the physical world, by treating the world as the program's test suite. We organize the discussion around three questions: how agents write programs for the physical world, how these programs are tested, and how agents learn from the results. We first trace how language models for robots and software engineering agents came together, ask which software testing practices carry over to physical tests, and describe each program by where it sits relative to the actuator and by what judges it. For writing, we cover programs that act as robot policies and programs that support policy learning by producing rewards, tasks, and training worlds. For testing, we examine what physical trials cost, what traces, learned judges, simulators, and formal checks can establish in their place, and what safety requires beyond task success. ===INTRO===

A coding agent is trying to put a moka pot on a stove. It is looking at four images taken just before and just after a simulated gripper attempted to grasp the pot’s handle. The fingers have closed on empty air beside it. The agent rereads the grasp routine it wrote an hour earlier and sees that it aimed at the center of the pot’s segmentation mask. It changes the target to the handle and runs the program again from fifty initial states. The pot is lifted in most of them. The agent writes a short note describing the failure and its fix and adds it to a library that agents working on other tasks will read. This is a composite scene with illustrative details, but systems such as ASPIRE already carry out this sequence of inspection, repair, validation, and reuse ( Lu et al., 2026 ) . Figure 2 draws the scene as a loop. The debugging loop is familiar from software engineering: run the program, inspect the failure, revise it, rerun it, and keep what works ( Yang et al., 2024b ; Wang et al., 2025 ; Jimenez et al., 2024 ) . Recent robotics systems reuse general-purpose coding agents for this work, giving them access to robot interfaces and execution environments. On manipulation benchmarks with task perturbations, these systems report success rates well above those published for end-to-end policies trained on demonstrations ( Lu et al., 2026 ; Elmaaroufi et al., 2026 ; Chu et al., 2026 ) . Validated programs can also generate successful trajectories for training those policies ( Wang et al., 2026m ; Shen et al., 2026 ) . In the opening scene, lifting the pot still leaves the task unfinished. Has the pot reached the burner, and is it upright and stable? The claim that it was lifted also depends on what the agent can observe and on what counts as a successful lift. In many software tasks, an existing test suite gives the agent a cheap, repeatable check on a proposed repair. For a physical task, the check may require observations, simulator state, or another trial, and its cost and reliability depend on how it is made. The literature shows both the value of execution feedback and the expense of obtaining it. In ASPIRE’s ablation on LIBERO-PRO, an execution engine and a skill library together raise macro-average success from 14% to 62%. The engine records perception and control calls, exposes images before and after them, and re-runs candidate repairs. Evolutionary search then adds another 10 percentage points ( Lu et al., 2026 ) . For programs that generate training environments, useful feedback can require training a policy on the environments they produce. A full Eurekaverse run incurs about 15 US dollars in language-model API costs and takes about 24 hours on eight A6000 GPUs ( Liang et al., 2024b ) . Beyond its cost, the judgment itself can be wrong ( Zhao et al., 2025 ; Zeng et al., 2025 ; Lin et al., 2025 ; Kong et al., 2025 ; Luo et al., 2026c ) . On FailBench, the best of thirteen detectors based on vision-language models (VLMs) reaches a macro-averaged balanced accuracy of only 0.77 when judging manipulation outcomes ( Navasardyan et al., 2026 ) . In OpenRUA’s analysis of failed episodes, about a quarter involve a success condition absent from the instruction or a predicate that contradicts it ( Chu et al., 2026 ) . These results motivate our central claim: for agents that write programs for the physical world, obtaining trustworthy evidence about program behavior is increasingly a limiting factor . We examine how this problem arises, what the available evidence supports, and how it shapes the design of agents, their memory, and their evaluation. ## 2 The Physical World as a Test Suite
We call the subject agentic intelligence for the physical world : work in which a model writes or edits a program whose effects are evaluated through physical execution on a robot, in a physics simulator, or through a policy trained with the program’s output. Where physical trial is not permitted, a model of the equipment the program controls can take the place of execution. Figure 2 shows the loop that these systems share. A model writes a program, the program runs in physical dynamics, a judge decides from what happened whether the program succeeded, and that result either guides a repair or adds the program to a skill library that later programs reuse. Each step of this loop has a counterpart in software engineering, where an agent edits a patch, executes it, checks the result against a test oracle, and merges a change that later work builds on. There, a test suite ties running, judging, and keeping together: it usually comes with the repository, and the agent can run it after every edit. Treating the physical world as the test suite means asking, at every step of the loop, what the world supplies in place of a test: which observations count as evidence, what an evaluation costs, how often a judgment is wrong, and what an accepted change commits later work to. To compare programs across this loop, we describe each one by two coordinates, defined in Section 2.4 : where the program sits relative to the robot’s actuators, and what judges it. Three research questions follow from the loop: RQ1 : What do programs buy an agent that acts in the physical world, and what do they cost? Where in the stack should the program sit, when does it outperform an end-to-end policy, and how should the two be combined? RQ2 : When the world is the test suite, how do agents learn that a program is wrong, and how far can that signal be trusted? What do traces, judges, simulators, and formal checks contribute, and what replaces physical trial when trial is not allowed? RQ3 : How does validated experience accumulate, and what shows that progress is real? When do skill libraries help or hurt, how far does their content transfer, and what must be reported for a result to be interpretable? Recurring terms are defined in the Key terms box on page 2 . 2.1 Scope and Definitions The ways a language model can direct a robot form a spectrum. At one end the model chooses one primitive at a time from a fixed menu. SayCan scores natural-language descriptions of pretrained skills, weights each score by a learned value function that estimates whether the skill can succeed from the current state, and executes the best skill ( Ichter et al., 2022 ) . Inner Monologue appends textual feedback, such as a success detector’s output or a description of the scene, before the model makes its next choice ( Huang et al., 2022b ) . Decisions are made step by step, with the dialogue providing the record of what has happened. At the other end, the model writes a program that makes those choices when it runs. Code as Policies made this concrete: a few-shot prompted language model writes Python that queries perception functions, does geometric arithmetic with NumPy and Shapely, and calls control primitives. The program may contain its own feedback loops ( Liang et al., 2023 ) . It can survive the episode that produced it, run from another seed, be compared with a previous version, and be stored for later tasks. A failing routine can be identified and edited.
