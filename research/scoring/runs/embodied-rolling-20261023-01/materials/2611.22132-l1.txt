===ABSTRACT===
Generating a LEGO model from a user request is more than a plausible 3D shape generation. LEGO models require physical support per brick, and each brick should be placed unblocked. Current methods address this issue by training an expert large language model. We reduce the problem of generating extremely long context on all brick connections to that of writing a program that builds LEGO models like a human, considering each intermediate step could be executed. We introduce DailyBrick , a multi-stage agentic system that produces a LEGO model together with a brick-by-brick assembly instruction for human building and robot assembly. We design a multi-stage harness with roles to help LLMs generate more effectively. A versioned construction SDK compiles multi-level decisions, from semantic subparts to individual bricks, into canonical operations. An external Meta-Reviewer agent replays and inspects the generated package, verifies the model and its construction process, identifies failures, traces them to the responsible stage, and routes them to bounded repairs or to editable candidates for later skill or tool updates. Extensive experiments demonstrate that DailyBrick generates LEGO models based on simple user requests better than recent agentic systems, and show its utility in downstream applications such as robot manipulations on model assembly from instructions and brick sets (https://SpatialAgent.github.io/DailyBrick/).

===INTRO===

Recent advances in 3D generation have made it possible to create diverse object models from text or images. For objects built from multiple parts, however, generating the final geometry does not by itself specify how those parts should be assembled. Assembly connects a desired object to a sequence of actions and intermediate steps, making it a useful setting for studying long-horizon planning, robot manipulation, and error recovery in embodied systems ( Sener et al., 2022 ; Heo et al., 2023 ) . Generating an object together with its assembly instructions could therefore provide both manuals for a human builder and downstream tasks for robot manipulation. Extending this goal to arbitrary real-world objects is challenging because their parts vary in geometry, connection mechanisms, and physical requirements. LEGO offers a controlled yet expressive setting for studying this problem. Its standardized catalogue defines atomic bricks with fixed geometries and specified connections, while their combinations support diverse objects and structural layouts ( Pun et al., 2025 ; Kulits and Schmid, 2026 ) . This setting allows us to study the generation of both a model and the brick-by-brick sequence that constructs it. Even with standardized bricks, a plausible LEGO model does not guarantee an executable assembly instruction. Each step must be compatible with the current partial assembly, making construction depend on both the spatial arrangement of bricks and their placement order. Existing approaches address different aspects of this problem. Image2Lego ( Lennon et al., 2021 ) directly fills a final voxel volume with bricks, while ASAP ( Tian et al., 2024 ) plans assembly sequences for known parts and target poses through disassembly search. BrickGPT ( Pun et al., 2025 ) integrates validity checks and physics-aware rollback into autoregressive brick generation. LegoACE ( Xu et al., 2025 ) encodes each brick as tokens, yet its authors report that some outputs remain disconnected. BrickNet ( Kulits and Schmid, 2026 ) further represents typed connections and checks construction prefixes for connectivity and collision. These methods advance assembly planning and model generation, but identifying an invalid step does not by itself determine which construction decision should be revised. A failed step may stem from a brick’s pose, an incompatible design, or an earlier structural plan. Linking the failure to the decisions that produced it is therefore important for targeted refinement. Recent agentic workflows offer a way by decomposing long-context generation into structured stages with intermediate outputs and feedback, enabling iterative refinement of generation programs ( Yao et al., 2023 ; Hong et al., 2023 ; Wang et al., 2024b ) . General-purpose coding agents such as Claude Code ( Anthropic, 2025 ) , Codex ( OpenAI, 2025 ) , and DeepSeek Harness ( DeepSeek-AI, 2026 ) can plan, write, and iteratively refine software with limited human supervision. ReAct ( Yao et al., 2023 ) and CodeAct ( Wang et al., 2024b ) connect language-model reasoning to tool use and executable actions, while MetaGPT ( Hong et al., 2023 ) coordinates specialized agent roles. In 3D generation, SceneSmith ( Pfaff et al., 2026 ) organizes scene construction into hierarchical stages, and Articraft ( Zhou et al., 2026 ) uses executable programs and feedback to refine generated designs. Applying these ideas to brick assembly requires connecting high-level structural decisions to individual placements, so that a failed construction step can be traced back to the decisions that produced it. Motivated by these observations, we introduce DailyBrick, an agentic pipeline that turns user requests into LEGO models and their step-by-step assembly instructions , reviewing each step and locating errors back to target stages or programs that need refinements. DailyBrick organizes the pipeline as a sequence of bounded stages, from overall layouts and semantic subpart designs to individual brick placement. A Planner-Designer-Critic workflow with separate contexts at each stage, passing only committed stage outputs to the next. Moreover, a Self Meta-Reviewer uses replay and provenance evidence to route detected defects to the implicated stage and stage output. It decides whether the current package(models and instructions) can be accepted or should trigger an update. Additionally, to bridge agents’ semantic planning and executable brick operations on LEGO models, we propose a versioned Software Development Kit (SDK). It supports both individual steps (colours, directions, brick ID) with partial assembly skills, allowing agents to express object-level plans as traceable step-by-step assembly instructions. Moreover, Self Meta-Reviewer replays the instructions to verify the result and locates errors in incomplete replay to update related stage, skills, or tools for refinement. ## 3 Method
As shown in Fig. 3 , DailyBrick takes a user request x and produces a LEGO model with step-by-step assembly instructions, or returns a failure report if the required checks cannot be satisfied. The optional image reference would be described as text content for input and verification. Each run uses an updatable configuration \Gamma , comprising P-D-C prompts, partial assembly skills and the SDK. The assembly instruction is represented by an assembly sequence \pi=(a_{1},\ldots,a_{T}) , where each action a_{t} specifies a brick placement. The resulting construction package is \mathcal{O}=(\mathcal{A}_{T},\pi,G,R), (1) where \mathcal{A}_{T} is the final LEGO model, G=(g_{1},\ldots,g_{T}) contains the instruction views, and R stores verification results and recorded generation dependencies. At step t , the instruction view g_{t} shows the placement a_{t} that transforms \mathcal{A}_{t-1} into \mathcal{A}_{t} . Each view g_{t} illustrates the placement a_{t} that transforms the partial assembly \mathcal{A}_{t-1} into \mathcal{A}_{t} . The model and instructions therefore describe the same construction sequence, which also provides part identities and ordered poses for downstream simulation and robot planning. Output package acceptance requires both successful verify replay under physical assembly constraints and a review of whether the generated design satisfies the user request. When a verify replay fails, the resulting evidence is passed to the Self Meta-Reviewer for error localizations and targeted updates. 3.1 Multi-stage Planning and Construction DailyBrick progressively translates the user request into a construction program through explicit stage outputs: x\longrightarrow\mathcal{B}\longrightarrow z\longrightarrow q\xrightarrow{\mathrm{Comp}_{\Gamma}}\pi, (2) where DesignBrief \mathcal{B} specifies the request, StructuralBlueprint z defines support layout and brick connections. AssemblyProgram q expresses the design through SDK operations. As shown in Fig. 3 , these representations summarize the eleven-stage workflow: early stages interpret the request, middle stages develop the structure and its subparts, and final stages compile and verify the assembly. Each stage receives defined inputs and produces an output checked against its requirements. Each agent-governed stage follows a Planner–Designer–Critic(PDC) loop. The Planner uses a pre-assigned stage role (fixed) and accepted upstream outputs to propose a local plan based on prompts. The Designer implements the plan within the stage’s permitted scope using the available skills and SDK operations. The Critic examines the candidate and requests revisions when needed, while a deterministic reviewer blocks outputs that violate construction requirements and stage roles. The stages use separate contexts and communicate through explicit outputs and feedback on PDC, where dialogues are not passed between stages. Accepted outputs retain their stage identifiers and dependencies, allowing later brick actions to be traced to the decisions that produced them. A refinement creates a new output version while preserving the earlier record. 3.2 Partial Assembly Skills and SDK The brick-construction SDK connects semantic plans to executable brick operations. Brick-level function calls specify the brick ID, colour, pose, connector, support dependency, and insertion direction. Partial assembly skills compose these calls into reusable procedures for subparts such as a wall, chassis, or roof. Each skill has a defined interface, preconditions, permitted read-write scope, and emitted actions, allowing agents to construct and revise local components within the overall design. Agents combine these operations and skills in an AssemblyProgram q=(u_{1},\ldots,u_{L}) . The deterministic compiler \mathrm{Comp}_{\Gamma} expands the program into the assembly trace \pi , recording the originating program operation for each step.
