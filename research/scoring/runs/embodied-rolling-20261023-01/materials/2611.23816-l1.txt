===ABSTRACT===
A patch to a robot's navigation software can pass every unit test and still drive the robot off its path. Checking how the repaired robot drives catches such patches. It does not show that the agent found everything that was wrong. We introduce RoboDx, a generator of repair tasks for simulated robot navigation software with known injected faults. A hidden verifier marks a repair as verified only if the robot then drives correctly in hidden scenarios, which the agent never sees. A second track hides the code and asks the agent to pick the cause from a list of hypotheses. A task with two faults can contain a quiet fault, a fault that makes no hidden scenario fail unless the other fault is also present. On our set of 100 tasks, RoboDx-Hard-100, almost every repair by Claude Opus 5.5 with standard coding tools is verified. We analyse 94 of the tasks, 44 with one fault and 50 with two. On the 50 two-fault tasks, only 17 of Opus's 49 verified repairs remove both injected edits. Most faults left behind are configuration constants whose correct value the task's documentation does not state. Opus names both faults on 10/50 of these tasks when it cannot see the code. We then give four current models the same measurements of each faulty robot, picked so that, in the simulator, only the true cause produces all of them. The models name the cause on at most 38 of 94 tasks. They are right on almost all when they also get the simulator's output for every hypothesis. Their own predictions of that output give no detectable gain. On 97 tasks from real bug-fix pull requests, Claude Haiku 5.5, the weakest model on the generated tasks, scores lowest, and the other three models are not ordered.

===INTRO===
A coding agent is asked to repair a robot that drives off its route. The robot’s navigation software has two faults. One line sets the heading gain ten times too low. The heading gain controls how hard the robot steers back toward its route, so the robot now turns sluggishly and misses waypoints, the points along its route. The other fault is a deleted speed cap. Without the cap the robot no longer slows down while it turns. With a correct heading gain the robot turns quickly, so alone the missing cap makes no test mission fail. The agent restores the gain. The robot then completes every test mission, and the repair counts as solved. The speed cap is still missing from the code ( Figure 1 ). Robot software holds much code like the speed cap. Speed caps, timeouts and safety stops do nothing until something else fails, so a check of the robot’s behaviour can miss them. Coding agents are now applied to robot software [ 34 , 37 , 72 ] , and finding the cause of a robot’s misbehaviour is a research problem of its own [ 46 , 44 , 58 ] . The closest benchmark for robot repair holds 33 real defects [ 104 ] . With real defects only the reported fault is known, so a fault that a repair leaves behind cannot be counted. Benchmarks built from repository issues, such as SWE-bench, grade a fix with the repository’s unit tests [ 52 , 114 ] . Unit tests accept wrong patches [ 92 , 82 , 110 , 5 ] . Table 1 sets a RoboDx task beside such a task. (i) The fix is graded by how the robot drives, because a wrong line can pass every unit test and still send the robot off its route. Faulty patches for robotic vehicles have been found by their effect on physical behaviour [ 63 ] . (ii) Every fault is known, because we inject it, so we can count the faults a repair leaves behind. That count matters because a fault can cause no failure unless a second fault is present, as with the missing speed cap. (iii) The cause is asked for directly. A second track hides the code and asks the agent to name the cause from measurements of the robot. We introduce RoboDx , a generator of such tasks and the hidden verifier that grades them ( Figure 2 ). The generator injects faults into correct navigation software that runs in a robot simulator. Each fault is a small edit of one of 143 kinds, such as a wrong change of coordinates or a wrong configuration value. A repair is verified if the robot passes every hidden check, among them 21 hidden scenarios , simulated missions that the agent never sees. A quiet fault is an injected fault that fails no hidden scenario unless the task’s other fault is also present. RoboDx-Hard-100 is our set of 100 generated tasks. We analyse 94 of them, 44 with one fault and 50 with two. A companion real set has 97 tasks from merged bug-fix pull requests of three open-source robot projects. RQ1: Does a verified repair remove every injected fault? A verified repair often leaves a fault in place. With standard tools, Opus has a verified repair on 98 of the 100 tasks. On the 50 two-fault tasks, only 17 of its 49 verified repairs remove both faults ( Section 4.1 ). RQ2: Can agents name the cause without the code? Opus often does on single-fault tasks and rarely on two-fault tasks. It names both faults on 10/50 of the two-fault tasks. A reference procedure that picks its measurements at random, and is given the simulator’s output for each hypothesis, is right on 47/50 ( Section 4.2 ). RQ3: What do agents lack when they miss the cause? Our evidence suggests that they lack the simulator’s output for each hypothesis. Shown the same measurements of the faulty robot, and choosing none themselves, four current models are right on 27 to 38 of 94 tasks. Adding that output raises them to 89 to 94, and their own predictions of that output give no detectable gain ( Section 4.3 ). RQ4: Do real bug-fix tasks separate the same agents? The real tasks separate the agents only in part. On the 97 tasks of the real set, Claude Haiku 5.5 scores lowest and the other three models are not ordered ( Section 4.4 ). A verified repair rate near 1.00 can make repair look solved. Of Opus’s 49 verified two-fault repairs, 32 still hold a fault. A benchmark that reports only the verdict does not count these faults. Opus, when it may ask a simulator what a hypothesis would show, names the cause on every task we analyse. This suggests that diagnosis agents need a way to simulate their hypotheses.
