# Can Astra Solve RoboMME without Breaking the Bank?

## Abstract
Robotic manipulation often requires remembering information that is no longer visible, such as an object's location before occlusion or the order of a demonstrated action sequence. A large vision-language planner can read this history, but calling it before every action chunk is slow and costly. We present a three-tier system for the RoboMME benchmark. GPT-6 Astra (System 2) selects a grounded subtask from stored visual history, a $π_{0.5}$ vision-language-action policy (System 1) executes it, and a fine-tuned Qwen3-VL-4B monitor (System 1.5) checks after each action chunk whether the subtask is finished. The instruction is kept until the monitor reports completion or a task-specific event occurs, while the policy keeps acting on new observations. On RoboMME, the system succeeds in 79.13% of episodes with an average of 3.63 Astra calls and 80.84 seconds per episode. This is 34.62 points above the best published non-oracle baseline and 4.95 points below GroundSG+Oracle, which gives the low-level policy ground-truth subgoals.

## 1 Introduction
Manipulation can depend on information that is no longer visible: an object’s identity before it is covered, the order of a demonstrated sequence, or the number of repetitions already completed. RoboMME [ 3 ] tests these dependencies with 16 tasks in four suites: Counting, Permanence, Reference, and Imitation. A common design for such tasks is hierarchical, with a vision-language model (VLM) choosing the next subtask and a vision-language-action (VLA) policy executing it. In our development runs, small high-level VLMs often misread RoboMME’s video inputs and issued wrong subtasks, so we use GPT-6 Astra [ 6 ] as the planner. Calling it before every action chunk, however, is expensive and mostly redundant: a chosen subtask usually remains valid for several chunks, and whether it has finished can be judged from the last few frames. We therefore place a small learned monitor between the planner and the policy. Astra is called at the start of an episode and again only when the monitor reports completion or a task-specific event occurs. In between, the VLA keeps executing the same instruction from fresh observations. We evaluate the full system on RoboMME and report success rates, planner usage, and failure cases. Related work. RoboMME compares symbolic and perceptual memory interfaces [ 3 ] . SAM2Act adds a visual memory bank [ 4 ] , MemER retrieves keyframes [ 8 ] , and MEM combines short-horizon video with long-horizon text memory [ 9 ] . Hierarchical systems such as \tau_{0} -VLA use execution memory and test-time reasoning to select subtasks [ 2 ] . Our system instead sends task-dependent history to an external planner at each call and lets a local monitor decide when to call it.

## 2 Three-Tier System
Figure 1 (a) shows the three components. Let g be the episode instruction, o_{t} the observation at environment step t , and l_{k} the k th grounded subtask. 2.1 System 2: History and Grounded Planning At each planning event, Astra produces one executable instruction: l_{k}\sim\pi_{\mathrm{HL}}(\,\cdot\mid o_{t},m_{t},g\,), (1) where m_{t} is the history passed to the planner. It has three parts: the demonstration video when the task provides one, selected execution frames that may show objects now hidden, and a text progress record that lists issued subtasks and monitor-confirmed subtasks separately. Repeated actions are recorded as separate entries, so their order and count remain available. Each request also includes the current front-camera image and the image at execution start. Astra keeps no state between calls; all history is sent with each request. Which history is sent and which output templates are allowed are configured per task: nine tasks receive the demonstration video and four receive dense execution history (Appendix B ; full prompts in Appendix D ). When a target must be localized, the instruction contains a pixel coordinate in the current image. The output is checked against the templates before it reaches the VLA. 2.2 System 1: Low-Level Action Execution We use RoboMME’s grounded-subgoal \pi_{0.5} policy [ 1 ] : a_{t:t+H-1}\sim\pi_{\mathrm{LL}}(\,\cdot\mid o_{t},l_{k},g\,),\qquad H=16, (2) where o_{t} includes camera images and robot state. Each chunk runs 16 environment steps. The same l_{k} can guide several consecutive chunks, and each chunk is predicted from a new observation, so control remains closed-loop while Astra is idle. 2.3 System 1.5: Visual Progress Monitoring The monitor is Qwen3-VL-4B-Instruct [ 7 ] , fine-tuned with LoRA on RoboMME demonstrations to predict a binary event for the active subtask: p_{\mathrm{MON}}(e_{t}\mid v_{t},l_{k},g),\qquad e_{t}\in\{0,1\}. (3) The input v_{t} has ten images: eight recent front-camera frames taken three steps apart (spanning up to 21 steps), the front image from when the current instruction was issued, and the current wrist image. This reference image is reset whenever an instruction is issued, even if its text repeats an earlier one, so each repetition is compared with its own starting state. In most tasks the event marks completion. In StopCube it signals an approaching target, and in ButtonUnmaskSwap Astra verifies a reported completion of the second button press (Appendix B.3 ). 2.4 Event-Triggered Coordination Astra is called once at initialization, and the monitor runs after every action chunk. A negative decision keeps the current instruction for another chunk. A completion event adds the subtask to the progress record and requests the next one. The StopCube timing event and the ButtonUnmaskSwap verification event send the execution history to Astra before the system advances. Figure 2 shows instruction reuse across one completion event; Appendix A gives full walkthroughs. Inference scheduling. As in RoboMME’s official two-system evaluation, the simulator pauses while Astra runs, so planning time adds to wall-clock duration but not to the step budget. In preliminary runs without pausing, the VLA used up the 1,300-step budget in most episodes before Astra returned.

## 3 Experiments
Setup. We evaluate on the official RoboMME test set (50 episodes per task) with a 1,300-step budget per episode and report simulator task success. Baseline numbers are the published RoboMME results [ 3 ] : \pi_{0.5} [ 1 ] with the current observation only; FrameSamp+Modul and SAM2Act+ [ 4 ] with perceptual memory; and MemER [ 8 ] , GroundSG+QwenVL, and GroundSG+Gemini with a high-level planner. The last two use a fine-tuned Qwen3-VL-4B [ 7 ] and a prompted Gemini 2.5 Pro [ 5 ] . GroundSG+Oracle gives ground-truth subgoals to the low-level policy and serves as a reference for grounded execution. The system reaches 79.13% overall success (Table 1 ): 94.00% on Permanence, 92.00% on Reference, 69.50% on Counting, and 61.00% on Imitation. Overall success is 34.62 points above FrameSamp+Modul, the best non-oracle baseline, and 4.95 points below GroundSG+Oracle. The gap to the oracle is largest in Counting (14.36 points, versus 3.17 in Reference and 2.98 in Imitation), and it comes mostly from StopCube: the other three Counting tasks average 86.67%. Failure cases. Of the 167 unsuccessful episodes, 103 fail and 64 time out. StopCube and InsertPeg each succeed in only 9/50 episodes and together account for 82 of them. StopCube requires pressing a button on a specific passage of a moving cube; all 41 of its unsuccessful episodes are failures rather than timeouts. InsertPeg requires contact-rich insertion; 36 of its 41 unsuccessful episodes time out. We have not yet attributed these failures to planning, monitoring, or execution errors. Appendix C lists outcomes for all 16 tasks. Planner usage. The system averages 3.63 Astra calls per episode, counting both planning and visual-verification requests, and 80.84 seconds of wall-clock time. The recorded trajectories contain 24.62 action chunks on average, so calling Astra before every chunk would require about 24.62 calls along the same trajectories.
