===ABSTRACT===
Large language models (LLMs) in embodied robots create security dependencies beyond inference. We investigate a network-exposed configuration attack on the Pollen Robotics Reachy Mini Lite, allowing an unauthenticated attacker to replace personality settings and the cloud LLM's system prompt through a management interface, without adversarial conversational input. Eleven prompt-injection attempts across five categories were reported as resisted, whereas both configuration-layer attack paths produced observable behavioural changes on physical hardware. We demonstrate local and network-adjacent access, mapping the weakness to CWE-306 (Missing Authentication for a Critical Function) and CWE-1327 (Binding to an Unrestricted IP Address), with a reported CVSS v3.1 score of 6.5 (Medium). A configuration endpoint also accepts cross-origin requests without a CORS preflight (CWE-352; 6.5 Medium), while the persistent-memory sink stores content without enforcing its stated restrictions. A source review of 59 public repositories identifies missing authentication in 10 of 11 source-verifiable genuine applications, or 11 of 11 including a framework-default case. These findings indicate recurrence within the sampled repositories, not prevalence in commercial products. We characterise a deployment gap between developer-oriented network assumptions and consumer-facing embodied AI security: inference-layer refusal cannot prevent unauthorised changes to model instructions. Potential consequences include surveillance through onboard cameras and microphones and social engineering of nearby user
===INTRO===

The recent advent of large language models acting as the cognitive component of physical robots has broadened social robotics, incorporating open-domain conversation, visual scene comprehension, and physical action for consumers and professionals ( Breazeal, 2003 ; Fong et al., 2003 ; Zeng et al., 2023 ) . Unlike common LLM uses, such robots are co-located with operators, so incident consequences extend beyond malicious text to the physical world: Breazeal ( Breazeal, 2003 ) found people hold qualitatively different trust expectations for physical versus digital agents, so a hacked social robot in a nursing home, school, or hospital poses a qualitatively different threat than a hacked chatbot. One under-examined property of such systems is their mandatory cloud dependency: because the LLM is cloud-hosted, the robot host needs constant network connectivity, and in the consumer deployment context evaluated here that connectivity is WiFi, placing the host on a shared local network that may include devices not controlled by the operator ( Zeng et al., 2023 ; Pollen Robotics, 2026 ) . This host is rarely bare: cloud-LLM robotics stacks commonly run a local companion application alongside the conversational pipeline, built on frameworks such as Gradio or FastAPI, so that a developer or operator can configure the robot’s behaviour from a browser without redeploying code. Network adjacency on its own is not the vulnerability; it becomes an attack surface only because that companion interface is bound to the network without authentication, here the Gradio interface on 0.0.0.0:7860 , so any device on the network can reach it. Existing research on LLM-controlled robot security has focused exclusively on the conversation interface ( Perez and Ribeiro, 2022 ; Robey et al., 2024 ; Shen et al., 2024 ; Zhang et al., 2024 ) , attacks that engage the LLM at inference and so must contend with its safety alignment. This overlooks the infrastructure below the LLM: the security boundary investigated in this work is the network-facing management interface rather than the LLM itself. In the evaluated deployment, an attacker with network reachability can submit configuration changes that alter the instructions subsequently supplied to the LLM before it has processed anything, rather than overriding them through conversation. In this paper, we demonstrate this class of attack on the Pollen Robotics Reachy Mini Lite (Figure 1 ). The personality management API exposes two unauthenticated endpoints on an interface bound to all network interfaces; a network-adjacent attacker with reachability to that interface can use two HTTP POST requests to change the robot’s AI instructions with attacker-controlled content. The attack takes under two seconds, requires no credentials, and in the local case persists across restart. The novelty of this work lies not in unauthenticated web interfaces or prompt injection individually, but in their composition in an LLM-controlled physical robot: network reachability enables unauthorised configuration modification, which changes the LLM’s system instructions and produces observable physical-system behaviour. This paper’s contribution is threefold: (1) Empirical: To the best of our knowledge, the first empirical demonstration, on a live consumer social robot, of a configuration-layer attack specifically against an LLM-controlled embodied system: an attack chain from unauthenticated, network-reachable API access through AI system prompt replacement to confirmed change in the robot’s verbal behaviour, without submitting adversarial conversational input at any stage. The underlying missing-authentication pattern is not itself new to robotics or IoT (Section 2 ); what is demonstrated here for the first time is its specific consequence for an LLM-controlled robot’s system instructions. (2) Conceptual: The deployment gap concept, characterising the structural security risk that arises when developer-first tooling frameworks reach consumer deployment without security review, as a candidate vulnerability class for embodied AI systems, together with a targeted repository survey (Section 5.2 ) measuring how far the pattern extends across the Gradio/FastAPI/Streamlit ecosystem beyond this single case. (3) Practical: A public release of proof-of-concept exploit code, a text-to-text pipeline modification enabling systematic testing, and an evidence archive, pinned to a specific commit of the target application, sufficient to reproduce the attack chain independently of whether the upstream project’s route layout has since changed. The vulnerability was disclosed to Pollen Robotics via private GitHub Security Advisory prior to the submission of this paper.

## 3. System, Threat Model, and Vulnerability Analysis
3.1. Target System The target system is the Pollen Robotics Reachy Mini Lite robot running reachy-mini-conversation-app version 0.8.0 (commit 81dfd7c ) on a Windows 11 PC ( Pollen Robotics, 2026 ) , with three layers: the physical layer (onboard camera, microphone array, speaker, head motors, USB 3.0 link to host); the application layer , resident on the host, which implements the personality configuration system and exposes the Gradio management API on TCP 7860 and a FastAPI hardware daemon on TCP 8000; and the cloud layer , the HuggingFace Realtime Speech platform hosting the LLM session over a WebSocket connection. A personality is a named configuration profile whose primary component, instructions.txt , holds the system prompt sent to the LLM at session start. Applying a personality disconnects and re-establishes the HuggingFace session with the new prompt as initial context, taking effect instantly and persisting across sessions if the persist flag is set. Started with the --ui flag, the Gradio server binds to 0.0.0.0:7860 , exposing the API on every interface including WiFi, so any device with network reachability to it can reach port 7860 without routing, with no mechanism to notify the operator. 3.2. Threat Model This unauthenticated binding is the entry point for every attacker position considered below, so the threat model that follows takes the exposed interface, not the LLM, as its starting boundary. It sits outside the usual white-box/gray-box/black-box axis ( Robey et al., 2024 ) , since the attacker never queries or interacts with the LLM at any point. With respect to the configuration interface, the attacker is black-box in the conventional sense, holding no credentials, no source access at attack time, and no prior interaction with the target. This is a fundamental departure from prior robot security research ( Robey et al., 2024 ; Zhang et al., 2024 ; Dorzhiev, 2026 ; Burbano et al., 2026 ) , all of which assumes an attacker who engages the robot’s conversation or perception interface and so must contend with alignment training. We consider three attacker positions. The primary attacker is any device sharing the host’s local WiFi network, requiring no physical access, no credentials, and no tooling beyond a browser or a Python environment with requests ; in consumer contexts this spans household guests, students on institutional networks, and visitors in care facilities. The secondary attacker is a malicious process on the host itself, targeting localhost:7860 ; on the Windows 11 host used here this position is reachable not only by locally installed malware but by an untrusted third-party application or a malicious browser extension, either of which can issue a direct loopback request or a local CSRF against the Gradio interface without needing to escape any sandbox, since the interface itself performs no authentication or Origin check. The tertiary attacker is a remote internet-based actor, relevant for the full Reachy Mini without firewall protection but not tested here. The threat model this paper establishes therefore spans both the network-adjacent WiFi position evaluated empirically and a compromised host environment, since the vulnerable endpoints make no distinction between the two once either is reachable. The primary attacker’s viability rests on an assumption built into most consumer WiFi deployments: devices sharing a subnet are mutually trusted peers, since access points authenticate once at association with no further per-device authorisation. This fails once a peer on that subnet is a management API with authority to rewrite a physically present AI agent’s instructions. An ARP sweep alone identifies every live host on a consumer /24 with free tooling, making an unauthenticated 0.0.0.0 bind not merely reachable but trivially discoverable. This assumption is not universal: many consumer access points and most enterprise and guest networks enforce AP (client) isolation, which blocks peer-to-peer traffic between wireless clients and would prevent the primary attacker position described here.
