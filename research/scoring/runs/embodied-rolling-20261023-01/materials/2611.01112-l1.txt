# Auriga Technical Report: A Task-Agnostic Agent Harness for Zero-Shot Embodied Manipulation

## Abstract
Vision-language models can interpret instructions and plan manipulation tasks, yet struggle when acting directly as robot policies. On RoboDojo, a large planning-execution gap separates high-level task decisions from physical execution: removing arm execution raises GPT-6 Astra's success rate from 22.5% under the reference control interface to 76.2%. We present Auriga, a task-agnostic agent harness that closes 68.3% of this gap in zero-shot manipulation without target-task trials or resets. In Auriga, the model makes all task decisions over an explicit task belief and acts through either direct tool calls or synthesized multi-step Python programs, while the harness supplies calibrated 3D measurements, finger-referenced dual-arm control, and a single admission gateway to the robot. Before motion, the model inspects a visual trajectory preview while simulation is paused; during execution, the harness checks declared stage tolerances and grasp bounds, stopping the robot on divergence and returning the measured discrepancy for in-place recovery. Developed across 13 cross-task capability iterations and frozen for evaluation, Auriga ranks first on the RoboDojo leaderboard with a 57.7% success rate (64.0 Score), more than doubling the reference harness on the same model, and remains first under scene randomization while learned policies drop by up to 33.9%. On RoboCasa365, the same frozen harness reaches a 73.2% success rate, outperforming VLA-assisted agents by up to 23.1% on composite tasks. Project page: https://auriga.stelledge.com/ Code: https://github.com/lose4578/Auriga

## 1 Introduction
“Plans are worthless, but planning is everything.” — Dwight D. Eisenhower In physical manipulation, a failed attempt changes the scene, often irreversibly. Unlike simulated settings where an agent can call env.reset repeatedly on a target task to tune coordinate offsets, control scripts, or failure notes before evaluation [ 11 , 20 , 31 , 49 ] , a deployed robot must complete an unseen task within a single episode. Tuning procedures across repeated trials on a fixed scene also fits to that scene’s layout, and performance drops when object positions are randomized or the task changes. Generalization in manipulation therefore separates two problems: across tasks during development, using failures to improve the shared perception, control, and verification tools rather than task-specific scripts; and during execution on an unseen task, completing the task in one episode without prior trials, demonstrations, or resets ( Sec. 2.1 ). On a 210-episode diagnostic across all 42 tasks of the RoboDojo benchmark [ 4 ] , the main bottleneck is physical execution rather than task reasoning ( Secs. 2.2 and 2 ). When GPT-6 Astra is given a privileged action that moves objects along chosen waypoints without the robot arm, it succeeds in 76.2% of episodes; when it drives the arm through the benchmark’s reference end-effector interface (RoboProbe [ 60 ] ), it succeeds in 22.5% . The model usually identifies the right object and destination, but the arm misses a grasp by a few millimeters, loses the object in flight, or hits a container rim during transport. Common control interfaces do not catch these errors in time. Step-wise and chunked action interfaces [ 37 , 62 , 60 ] issue motions from the latest frames without showing the full route in advance, so collisions appear only after the arm has moved. Program generation [ 21 , 9 ] hands execution to a script that cannot see the scene, where normal program exit does not mean the intended contact succeeded. We present Auriga , a task-agnostic agent harness that narrows this planning–execution gap within a single zero-shot episode ( Figs. 1 and 2 ). In Auriga, the model makes all task decisions, while the harness measures the scene, checks and executes motions, and reports what happened: 1. Task-agnostic harness and explicit task belief ( Sec. 3 ). Auriga contains no task-specific code, prompts, or heuristics, and exposes no privileged simulator state. One persistent model session plans the task, chooses actions, and recovers from errors. As an episode grows long, the model records its current plan, open questions, and task premises ( pending , supported , contradicted , or unknown ) in a concise task belief B_{t} , while full interaction logs stay in an off-context evidence record E_{t} retrieved on demand. 2. Preview and verification through a single admission gateway ( Sec. 4 ). Every physical motion, whether called directly or from a model-written program, passes through the admission gateway \mathcal{A} in a preview–execute–verify loop. While simulation is paused, \mathcal{A} plans a multi-stage dual-arm sequence into a trajectory preview showing the path, step cost, and clearance warnings. During execution, the previewed trajectory runs while \mathcal{A} checks model-set arrival tolerances \tau_{k}=(\delta_{p},\delta_{\theta}) , gripper openings, and observation checkpoints. If a stage misses its tolerance, \mathcal{A} stops the robot and returns a receipt r_{t} with the completed stages, measured deviations, unexecuted stages, and fresh camera views so the model can recover from the current state ( Fig. 2 ). 3. 3D geometric measurements and finger-referenced actions ( Sec. 5 ). On the input side, camera calibration, VGGT-Omega [ 46 ] depth, and SAM 3.1 [ 2 ] segmentation provide 3D object estimates, ray–plane intersection with height sensitivity, and two-view triangulation, together with in-hand slip measurements and warnings when a motion re-enters a past failure region. On the output side, the model sets goals at the finger contact region rather than the wrist, chooses tolerances per stage, and coordinates both arms on a shared timeline. Auriga separates cross-task tool development from single-episode execution ( Secs. 2.3 and 2.3 ). Over 13 development iterations ( Fig. 3 ), manipulation failures were used to identify missing capabilities in 3D localization, contact checking, and state tracking, raising zero-shot performance across all 42 RoboDojo tasks from 36.2% SR (45.5 Score) at iteration #4 to 57.7% SR (64.0 Score) in the final harness. During evaluation, the harness is frozen and runs under the single-episode zero-shot protocol ( Secs. 2.1 , 6.1 and 6 ), with no target-task exploration, demonstrations, or resets: • RoboDojo [ 4 ] . ## 2 Problem Setting and Positioning
We study zero-shot manipulation, in which a general-purpose model uses a shared robot harness to construct and execute a task procedure from the task specification and interaction feedback. We first define the single-episode zero-shot evaluation protocol ( Sec. 2.1 ), then quantify the planning–execution gap that motivates our harness ( Sec. 2.2 ), and finally position cross-task harness evolution relative to within-task trial search ( Sec. 2.3 ). 2.1 Zero-Shot Single-Episode Protocol Task and interaction. The unit of evaluation is a case , defined by a task instruction and a specified scene variant, random seed, and layout. Each case starts from an initial scene and is evaluated under the benchmark’s execution budget and success criteria. The agent receives the task specification and accesses observations and robot actions through the shared harness. It uses the available observations and interaction history to choose subsequent tool calls or programs, then receives feedback from their execution. This interaction continues until success, termination, or budget exhaustion. The benchmark’s evaluator determines task success from the resulting execution. Zero-shot protocol. We define zero-shot evaluation through three conditions: 1. No target-task exploration or development before evaluation. Evaluation starts with a pretrained model, a fixed shared harness, and task-independent operating guidance. No preparatory exploration or trials are conducted on the target task, including its other layouts, to develop or select task-specific prompts, programs, skills, or policies. Model parameters remain fixed throughout evaluation. 2. No demonstrations at evaluation time. The agent receives the task specification and permitted observations, without additional solution examples or expert demonstrations. For memory tasks, the benchmark-defined event sequence forms part of the case’s observation input. 3. One execution per case. Each case is initialized and executed once, without a reset or rerun.
