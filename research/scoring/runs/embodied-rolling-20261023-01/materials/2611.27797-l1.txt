===ABSTRACT===
Long-horizon embodied tasks require agents to ground instructions in changing observations, coordinate heterogeneous tools, and recover from failures that can propagate through downstream operations. Although existing LLM-based agents retain experience and refine reusable skills, successful local repairs do not by themselves establish complete-task gains over the current shared procedure library. We present EvoTER, an experience-driven framework that enables embodied agents to self-evolve tool-use skills without updating model parameters. EvoTER operates through a three-role evolution loop: Explorer records tool-use trajectories; Diagnoser distills successful and failed executions into skills for tool selection, parameter computation, postcondition checks, and recovery; and Validator retains candidate revisions only when they improve complete-task success in fresh sessions. In simulation, EvoTER improves overall task success from a pre-evolution baseline of 53.60% to 80.40%. In real-world experiments, simulation initialization reduces the attempts required to acquire short-horizon skills, while continued real-world evolution improves long-horizon success from 20% to 80%-100% across tasks and enables the evolving skill library to incorporate new tool functionality introduced after simulation development. Project page: https://evoter-project.github.io/

===INTRO===
Large language models (LLMs) enable embodied agents to translate natural-language instructions into executable programs over robotic APIs [ 1 , 2 ] . By interleaving reasoning, tool calls, and execution feedback, LLM-based agents coordinate perception, planning, and control for multi-step tasks [ 3 ] . Integrating pretrained visuomotor policies, including vision-language-action (VLA) models, further extends this repertoire by combining learned manipulation behaviors with conventional robotic tools [ 4 ] . However, reliable long-horizon execution remains challenging, as errors in perception, tool coordination, and physical interaction can propagate across dependent steps. These challenges motivate four complementary capabilities for reusable tool-use procedures: (i) Grounding : deriving tool arguments from current observations [ 1 ] ; (ii) Composition : coordinating heterogeneous tools as subtasks and scene conditions change [ 4 ] ; (iii) Verification : checking physical outcomes and recovering from execution deviations [ 5 ] ; and (iv) Adaptability : supporting reuse and refinement under changing physical conditions and tool interfaces [ 6 ] . These capabilities interact during execution, complicating procedure reuse across changing task states and environments. Existing agents exploit execution feedback at different levels: closed-loop agents use it for execution and recovery [ 3 , 5 ] , but such corrections do not necessarily yield reusable knowledge. Memory-guided agents retain experience [ 7 , 4 ] , while self-improving systems revise reusable skills [ 6 , 8 ] . In tool-use settings, such revisions can modify tool selection, state-dependent parameter computation, sequencing, and recovery. Recent approaches assess revisions in different ways: transfer studies validate memory or stack updates before frozen target evaluation [ 9 , 10 ] , whereas feedback-driven systems use execution and regression checks during refinement [ 6 , 8 ] . However, successful repairs or regression checks do not necessarily establish complete-task gains over the current shared library, as local changes may affect downstream operations. This issue becomes particularly relevant after sim-to-real transfer, where physical feedback can reveal new failures and motivate further revisions. With model parameters and tool implementations fixed within each evolution phase, we ask: How can agents select revisions based on complete-task gains over the current library to continually evolve reusable tool-use procedure libraries for long-horizon tasks across simulation and real-world refinement? To address this question, EvoTER evolves a persistent library of reusable, observation-grounded tool-use skills through feedback-driven revision and comparative complete-task acceptance. These skills support heterogeneous tool composition, postcondition checks, and recovery. The evolution loop comprises three roles sharing a frozen multimodal LLM: Explorer collects execution trajectories, Diagnoser identifies failures and proposes revisions, and Validator compares candidate and current libraries on matched complete-task runs. Only revisions improving aggregate complete-task validation success over the current library are retained. Model parameters, tool implementations, and evaluation settings remain fixed per evolution phase for controlled comparisons. Privileged simulation feedback may aid diagnosis, while skill execution and validation rollouts use only deployment-available observations and tools. Validated simulation skills initialize real-world evolution, where physical feedback triggers further revision-and-acceptance cycles. In simulation, EvoTER achieves a 26.80 percentage-point gain in overall task success over its pre-evolution baseline. On real robots, simulation initialization reduces short-horizon skill-acquisition attempts, while continued evolution adapts long-horizon procedures to real-world conditions and tool interfaces. Our contributions are as follows: • We propose EvoTER, a framework organizing tool invocation, composition, outcome checks, and recovery into reusable, observation-grounded skills for long-horizon tasks without updating model parameters. • We introduce an Explorer–Diagnoser–Validator loop that turns execution and simulation data into skills for real-world use, selects revisions by task-success gains, and continues evolving skills from real-world feedback. • We demonstrate superior performance in simulation, and real-world experiments further confirm that simulation-initialized skills reduce development attempts while continued evolution supports long-horizon execution.

## III METHOD
EvoTER updates an embodied agent’s skill library by converting tool-use experience into reusable skills through reflection and validation. The framework comprises an embodied tool-use agent ( Sec. III-B ), an experience-driven skill evolution loop ( Sec. III-C ), and a sim-to-real skill transfer and adaptation process ( Sec. III-D ). Fig. 1 presents the framework overview, with each component detailed below. III-A Problem Formulation Embodied Agent and Skill Library. We consider embodied agents that execute natural-language task instructions through tool calls. On platform p\in\{\mathrm{sim},\mathrm{real}\} , we define the agent at evolution iteration r as \mathcal{A}^{(p)}_{r}=\left(M,\mathcal{T}^{(p)},h^{(p)},\mathcal{S}^{(p)}_{r}\right), (1) where M is the model backbone, \mathcal{T}^{(p)} the ordinary tool registry, h^{(p)} the execution harness configuration, and \mathcal{S}^{(p)}_{r} the persistent skill library. Each skill specifies applicability conditions, tool-call rules, parameter computation, postcondition checks, and recovery instructions, with optional executable scripts. Within each evolution phase, model parameters, ordinary tool implementations, and harness configuration remain fixed; the agent evolves by updating \mathcal{S}^{(p)}_{r} . Skill Evolver. A skill evolver converts the agent’s execution experience into persistent updates to its skill library. Let \mathcal{B}_{r} denote execution evidence collected by \mathcal{A}^{(p)}_{r} on development instances. The evolver \mathcal{U} proposes and validates skill updates to produce the next library: \mathcal{S}^{(p)}_{r+1}=\mathcal{U}\!\left(\mathcal{S}^{(p)}_{r},\mathcal{B}_{r};\mathcal{X}_{\mathrm{val}}\right), (2) where \mathcal{X}_{\mathrm{val}} is a reserved validation set for assessing candidate updates. The operator includes update proposal and acceptance; rejected updates leave the library unchanged. Accepted updates persist for subsequent execution and evolution. EvoTER implements this process through three roles, Explorer, Diagnoser, and Validator, detailed in Sec. III-C . Evolution Objective and Evaluation. Task instances are indexed by (\kappa,\xi) , where \kappa denotes the task and \xi its initial scene configuration. Let \mathcal{X}_{\mathrm{dev}} and \mathcal{X}_{\mathrm{test}} be disjoint sets of task–seed pairs, with \mathcal{X}_{\mathrm{val}}\subset\mathcal{X}_{\mathrm{dev}} reserved for intermediate validation. For a fixed platform, let \pi_{M} be M ’s policy and y(\kappa,\xi;\pi_{M},\mathcal{S})\in\{0,1\} the externally evaluated task outcome. The task success rate (SR) on \mathcal{X} is \mathrm{SR}(\mathcal{S};\mathcal{X})=\frac{1}{|\mathcal{X}|}\sum_{(\kappa,\xi)\in\mathcal{X}}y(\kappa,\xi;\pi_{M},\mathcal{S}). (3) We aim to convert execution experience into reusable skills that improve task success under the fixed execution system. Candidate acceptance depends on success rate on \mathcal{X}_{\mathrm{val}} . After development, the skill library is frozen and evaluated on \mathcal{X}_{\mathrm{test}} , which informs neither skill updating nor selection. III-B Embodied Tool-Use Agent We formulate embodied execution as the composition of fixed tool capabilities guided by an evolving skill library. Tools provide the agent’s executable capabilities, while skills encode procedural knowledge about their use across task states. The frozen model combines this knowledge with the task instruction and interaction history to select tools, determine their arguments, and assess execution outcomes. This separation allows skill updates to change the agent’s execution behavior without modifying the model, tool implementations, or harness configuration. Fixed Tool Capabilities. The registry \mathcal{T}^{(p)} exposes observation, perception, planning, control, and policy capabilities through tool interfaces, including open-vocabulary segmentation and detection [ 21 , 22 ] , grasp generation [ 23 ] , and collision-free motion planning [ 24 ] . Each tool specifies its purpose and input–output schemas for model invocation. Simulation and real-robot platforms expose corresponding tool types with platform-specific implementations. Reusable Procedural Knowledge. The skill library \mathcal{S}^{(p)}_{r} stores procedural knowledge that guides tool selection and composition. Each skill specifies when it applies, how to invoke tools and compute their arguments, check postconditions, and recover from unsuccessful execution. Skill summaries support selection, and loaded skills provide detailed execution guidance. Associated scripts may compute observation-grounded tool arguments from current non-privileged observations using ordinary tool interfaces. The library remains fixed within an episode. When \mathcal{S}^{(p)}_{0}=\varnothing , the model acts directly from the tool descriptions. Feedback-Driven Tool Composition. At execution step t of evolution iteration r , the frozen model selects a tool call conditioned on the instruction \ell_{\kappa} , observation o_{t} , history \mathcal{H}_{t} , and current skill library: a_{t}=(\tau_{k_{t}},\phi_{t})\sim\pi_{M}\!\left(\cdot\mid\ell_{\kappa},o_{t},\mathcal{H}_{t},\mathcal{S}^{(p)}_{r}\right), (4) where \tau_{k_{t}}\in\mathcal{T}^{(p)} and \phi_{t} denotes its arguments. The harness executes the call and adds feedback f_{t} and observation o_{t+1} to the interaction history. The agent uses this evidence to check the active skill’s postconditions, proceeding if satisfied; otherwise, it follows recovery guidance or replans from the current state. Observed outcomes thus guide tool composition throughout execution. Episodes end upon task completion, terminal failure, or tool-call budget exhaustion. Each episode produces an execution record that links tool decisions to their observed consequences: \rho=\left(\{(o_{t},a_{t},f_{t},o_{t+1})\}_{t=0}^{L-1},y\right),\hskip 16.38895ptL\leq H, (5) where L is the number of tool calls, H is the call budget, and y is the externally evaluated task outcome. These records and associated images, videos, and logs support skill diagnosis, refinement, and validation. III-C Experience-Driven Skill Evolution Skill evolution requires extracting reusable execution rules from interaction trajectories and evaluating their effectiveness under deployment conditions. EvoTER organizes this process into three roles: Explorer \mathcal{E} collects execution experience, Diagnoser \mathcal{D} analyzes execution and revises skills, and Validator \mathcal{V} evaluates candidate updates. The roles share the same frozen model but operate with distinct input contexts and tool permissions. Each role transition initiates a new session with the corresponding context and permissions. Execution trajectories, diagnostic records, and skill versions are exchanged through external files, while the skill library retains deployment knowledge accumulated across tasks. Explorer. Successful trajectories reveal reusable tool combinations and parameter choices, whereas failed trajectories help identify limitations in the current execution rules. Explorer collects both types of experience during task execution. For a development instance (\kappa,\xi)\in\mathcal{X}_{\mathrm{dev}}\setminus\mathcal{X}_{\mathrm{val}} , Explorer starts a new session and executes the task using the current skill library and ordinary tool registry \mathcal{T}^{(p)} . The execution procedure matches that used for evaluation with the skill library frozen. After each task, the recorded tool calls, execution feedback, images, and videos are passed to Diagnoser for skill extraction and failure diagnosis. Diagnoser. Task outcomes alone do not reveal which tool calls or execution rules require revision. Diagnoser examines execution trajectories, the current skill library, and diagnostic records to relate tool calls to observed environmental changes. From successful executions, it extracts reusable tool combinations, parameter computation methods, and postcondition checks. For failed executions, it uses logs, tool outputs, keyframes, and videos to locate execution failures. Diagnostic retries test alternative invocation parameters and recovery rules, providing evidence for candidate revisions. When a task makes no progress over consecutive evolution iterations and reaches a predefined stagnation threshold, simulation diagnosis accesses \mathcal{T}_{\mathrm{priv}} . This interface provides simulation state, task predicates, and privileged planning tools for failure analysis and recovery testing. Additional information from diagnosis must be converted into rules executable under deployment conditions. The skill-generation prompts require revisions to be grounded in currently observable tool outputs and associated scripts to compute invocation parameters from current observations. These prompts also prohibit embedding privileged coordinates, simulator object identifiers, or seed-specific constants directly in skills. Diagnoser produces a diagnostic report d and a skill update \Delta\mathcal{S} . Based on execution evidence and the current library, it decides whether to refine an existing skill or add a new entry, forming a candidate library: \displaystyle(d,\Delta\mathcal{S}) \displaystyle=\mathcal{D}\!\left(\{\rho_{i}\}_{i=1}^{N},\mathcal{S},\mathcal{T}_{\mathrm{diag}}^{(p)}\right), (6) \displaystyle\mathcal{S}^{\prime} \displaystyle=\mathcal{S}\oplus\Delta\mathcal{S}. Here, \mathcal{S}=\mathcal{S}^{(p)}_{r} is the current library, and \mathcal{S}^{\prime} is the candidate awaiting validation. The set \{\rho_{i}\}_{i=1}^{N}\subseteq\mathcal{B}_{r} contains the N input trajectories, and \oplus denotes the skill-update application.
