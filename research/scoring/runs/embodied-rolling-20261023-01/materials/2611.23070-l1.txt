===ABSTRACT===
Household robots often need to operate appliances, and smart appliances offer both control panels and device APIs. Existing embodied AI simulation environments, however, model appliances solely as physical objects. We introduce PAIR, a smart-home simulation environment grounded in the Matter protocol~\footnote{https://csa-iot.org/all-solutions/matter/}, the industry standard for smart-home devices. PAIR provides 84 smart-device assets whose functional control panels and APIs act on a shared device state, with ambient conditions that evolve in response to both. From a survey of 1,443 requests, we construct a benchmark of 40 tasks that all require object manipulation yet remain solvable without API access, with 340 human demonstrations for policy training. Whether run alone, with a high-level planner, or with an API-enabled planner, two fine-tuned VLA policies complete none of the 120 evaluation episodes. Robots rarely get far enough to use the API: even with oracle plans and API access, over 90\% of failed rollouts stall at navigating, grasping, or operating a door. With a perfect oracle in place of the robot's body, the best planner still gets through only 57.3\% of its plan. When choosing between pressing a button and calling an API, several planners go by whether they can read the panel, not by API latency.\footnote{We will release our code and data upon publication.}

===INTRO===

Building household robots that assist people with everyday tasks is a long-standing goal of embodied AI [ 9 , 29 , 12 ] . Performing these tasks often requires robots to operate household appliances by manipulating their controls, such as pressing buttons, turning knobs, and navigating touchscreens. Modern smart appliances, however, increasingly provide application programming interfaces (APIs), which allow external systems to read device states and send control commands through software [ 5 , 1 , 7 ] . Household tasks often involve both physical actions, such as navigation and object manipulation, and appliance operations that can be performed through APIs. Therefore, household robots need to flexibly select and combine physical actions and API calls to accomplish everyday tasks efficiently. For example, the request “Wash my shirt,” requires a robot to physically load the shirt into the washing machine and close the door. Once the door is closed, the robot can start the cycle and monitor its progress through the API, without operating the control panel. Studying how robots execute such tasks at scale calls for a simulation environment where device states change over time and where physical actions and API calls operate on the same devices. Existing simulation environments [ 14 , 12 , 17 ] provide rich physics-based environments for robot manipulation, but they treat appliances as objects to be physically operated and do not consider smart-home settings, where devices report their states and accept commands through APIs. To bridge this gap, we introduce PAIR (Physical-API Integration Environment for Robots), a smart-home simulation environment that integrates physical and API-based device control. In PAIR, device states progress over time and respond to both physical actions and API calls, and running devices in turn change four ambient conditions of the home (temperature, illuminance, humidity, and air quality). We develop 84 smart-device assets , each with a functional physical interface and an API, across 14 appliance categories and four sensor categories that report these ambient conditions. Device states, commands, and operational constraints are defined according to the Matter protocol [ 5 ] , an industry standard for smart-device interoperability. To ground evaluation in what people actually want from such a robot, we surveyed 129 participants about device-related household tasks they would delegate to a mobile manipulator capable of handling objects, operating appliances, and remotely controlling smart devices, and retained 1,443 requests from 108 participants after screening. We label each request with the skills it requires, using a taxonomy of robot skills in three categories, physical, perception, and human interaction (Table 1 ). More than half of the requests (58.4%) involve checking a device’s status or waiting for an event, and APIs alone could complete only 39.6% of them, while the remaining 60.4% also require the robot’s physical actions or perception. From these requests, we construct a benchmark of 40 tasks that cover the skills in our taxonomy and all device categories in PAIR. Every task requires object manipulation yet can be completed without API access, so the same task can be evaluated with and without APIs and across policy architectures. Using this benchmark, we investigate how well current vision-language-action (VLA) policies handle such tasks. To adapt them to our robot and tasks, we collect 120 task-level demonstrations (three per task) and 220 demonstrations of atomic skills, all performed without API access. We then evaluate these policies alone, with a high-level planner, and with a planner that has API access, comparing task success and execution steps and analyzing how performance varies with the skills each task requires. None of the six VLA variants completes an evaluation task. API access raises device-operation success, yet with oracle plans and API access, more than 90% of the failed rollouts still stop at a navigation, pick, or door subtask. Even with oracle physical execution, the best planner reaches only 57.3% Progress, and several planners choose the API in response to panel visibility more consistently than to the stated API delay.

## 3 PAIR
We present PAIR, a smart-home simulation environment that integrates physical and API-based device control, building on OmniGibson [ 12 ] for physical simulation. Figure 2 illustrates the overall system architecture. 3.1 Smart-Device Assets To support the realistic physical operation of smart-home devices, we construct 84 functional smart-device assets across 18 device categories, 14 of appliances and four of sensors. We source one to three appliance bodies per category, primarily from high-fidelity ArtVIP assets [ 8 ] , supplemented with appropriately licensed third-party assets. Inspired by real-world household appliances, we manually design and implement three functional control-panel variants (P1–P3) for each body, as exemplified in Figure 3 . Each panel provides a control for every function and a display or indicator for every state of the underlying Matter-based device model. Compared with our measurements of commercial appliances, its buttons and knobs are somewhat larger and its displays are of similar size. We further evaluate the perceived realism of the resulting assets through human evaluation, obtaining an average realism score of 4.63/5 (Appendix ). Details on asset sources, licenses, panel measurements, and device-specific physical interfaces are provided in Appendix A.1 . 3.2 Agent Interface Agents in PAIR interact with the environment through two channels: physical actions and API calls. For physical actions, agents receive visual observations of the environment and execute actions such as navigation, object manipulation, and device operation. Device indicators, panel displays, and sensor displays provide visual access to device states and ambient conditions. For API calls, we use SimuHome’s Matter-based device model [ 23 ] to represent networked device states and commands. Agents can identify target devices, inspect their available attributes and commands, query device and sensor states, and issue device commands with the required arguments through structured APIs. Commands that cannot be executed given the device’s current state and operational constraints are rejected without changing the device state. The full list of API tools is provided in Appendix . Spoken Cue Recognition, Informing 3.3 API–Physical State Coupling To maintain consistency between these two channels, PAIR uses a shared device state that can be updated through either channel. Changes to this state are reflected in the device’s physical behavior and observable feedback, and, where applicable, drive the evolution of ambient conditions. We implement this coupling in both directions as follows. Updates from API Calls. When an API command is executed, it updates the shared device state, with corresponding changes reflected in the device’s physical behavior and observable feedback, such as control-panel displays and indicators. We additionally model network communication as a configurable one-way delay d , set to 200 ms by default based on message-delivery delays of up to 200 ms observed in prior measurements of Matter in an indoor home environment [ 15 ] . Accordingly, a command takes effect after d , and the response returns to the agent after a total round-trip delay of 2d . A state query similarly reads the shared device state after d and returns the observed value after 2d . Updates from Physical Operation. Physical operations update the shared device state locally according to the device’s operational constraints, with the resulting changes reflected in the corresponding API-exposed state and observable feedback. Unlike API calls, physical operations are applied locally rather than transmitted over the network, so we introduce no additional communication delay for them. For example, pressing the power button on a smart light updates its power state, changes the corresponding observable feedback, and affects the room illuminance.
