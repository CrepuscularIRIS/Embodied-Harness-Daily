# ReSkill: Selective Self-Improvement for Robot Manipulation

## Abstract
Self-improvement on compositional manipulation tasks requires deciding what to reuse, where to improve, and which changes to retain. We present ReSkill, a selective self-improvement framework that concentrates revision on capability gaps. A coding agent constructs an object-centric task graph from an instruction and a skill library, then uses node-level execution records to locate failures. At the task level, it revises stage organization, hand-off conditions, and recovery routes; at the skill level, it strengthens perception, motion, manipulation, and verification capabilities that repeatedly fail. Candidate revisions undergo full-task evaluation and paired comparisons before adoption, allowing local changes to accumulate into validated skills and an independently executable policy. The agent participates only during development; the deployed policy calls the retained skills without invoking the agent at run time. On the same development set, average success across ten RoboDojo tasks rises from 30.0% for the initial versions to 86.2% for the final adopted programs; retained programs achieve 83.6% in recorded robustness and model-selection evaluations. Across eight real-world tasks, ReSkill succeeds in 72 of 80 rebuilt-simulation trials and 62 of 80 real-robot trials (77.5%). The median revision changes only three functions, approximately 0.5% of a program, while 39% of task-specific functions in later-added tasks directly reuse existing implementations. These results show how locating local deficiencies, validating candidate changes, and accumulating reusable skills can improve execution of compositional manipulation tasks.

## 1 Introduction
When a robot encounters a new manipulation task, the capability it lacks often covers only part of the task. A compositional task may involve observation, approach, grasping, transport, placement, and return; existing controllers or skills can already handle many of these stages, while a few fail on new objects, layouts, occlusions, or execution conditions. Robot foundation models have expanded robots’ ability to act on visual and language inputs [ 23 , 1 ] , while language-model agents have enabled flexible task decomposition and skill coordination [ 6 , 7 ] . Nevertheless, new multi-stage tasks are often treated as unified learning or adaptation problems. This can require relearning capabilities the robot already has and increase the costs of data, computation, and real-world interaction. This raises a more fundamental question: when a robot encounters a new compositional manipulation task, what exactly should it improve? Existing research addresses this problem through end-to-end policy learning, skill composition, and agent self-improvement, but still lacks explicit modeling of where capability gaps occur. End-to-end policies map observations and task instructions directly to actions [ 23 , 1 ] , making it difficult to distinguish stages that already work reliably from those that need improvement. Agentic manipulation systems based on task decomposition, programmatic control, and skill calls [ 6 , 7 , 13 , 5 ] flexibly compose existing capabilities, but mainly improve how those capabilities are organized and used: when a skill repeatedly fails under new conditions, replanning or calling the same skill again does not change the skill itself. Voyager accumulates executable skills, Reflexion stores reflections from task feedback, and Self-Refine iteratively critiques and revises model outputs [ 17 , 12 , 11 ] . For robot manipulation, candidate revisions must also be assessed across layouts: an improvement on a few development scenes may not persist under different initial conditions. The unresolved question is therefore: how can a robot first locate the capability gaps in a task, improve only those parts, and reliably judge whether the improvement is real and worth retaining and reusing? We introduce ReSkill, a framework for selective self-improvement on compositional manipulation tasks (Figure 1 ). The robot first identifies the task structure and assesses its existing capabilities, then concentrates improvement on the gaps that remain. A coding agent serves as the learning orchestrator, constructing an object-centric task graph from a task description and, optionally, one demonstration. Each node specifies a skill call, its object roles, entry and completion conditions, and budget; edges specify success, failure, and recovery routes. Within this graph, explicit geometric routines handle stages that can be programmed directly, and library skills cover interactions the robot already knows how to perform. Repeated execution failures reveal the unresolved stages or skills and direct the agent’s revisions, allowing development to preserve and build on capabilities that already work. Improvement proceeds at two scales, using the same node-level execution records and visual traces. At the task level, the agent locates the earliest stage that deviates and revises stage decomposition, hand-off conditions, skill bindings, or recovery procedures. For example, in cup nesting it changes the release-stage completion condition to require both release and the intended nesting relation, while keeping the grasping and insertion skills unchanged. At the skill level, improvement is organized around four types of reusable capability: perception skills estimate object geometry, motion skills generate feasible trajectories, manipulation skills perform interactions such as grasping and placement, and verification skills check outcomes and guide correction. Failure evidence accumulated across tasks identifies which skill needs strengthening; validated improvements are shared through the skill library or transferred into other task programs. New tasks therefore start from the existing task with the closest skill requirements. Every revision at either scale must pass multi-stage evaluation before adoption. Candidates are screened on a few development layouts, evaluated on the full development set and robustness layouts, and compared with the incumbent on paired test layouts available only to the orchestrator. When results are close, paired evaluations are repeated on layouts where outcomes disagree. This links local revision to evidence that determines whether an improvement should be retained and reused. We evaluate ReSkill on ten RoboDojo simulation tasks [ 3 ] and eight real-world tasks on the Xtrainer platform. ## 2 Methods
2.1 Problem setting and overview We study how to construct a reusable task program for a new compositional manipulation task while concentrating development resources on the parts that existing capabilities do not cover. Given a task description \ell (a natural-language instruction and a description of the success criterion), the robot’s observation and control interfaces, and optionally one demonstration \tau^{D} , the system outputs a task program \mathcal{P}=\bigl(G,\ \Pi,\ \Lambda\bigr), (1) where G is an object-centric task graph, \Pi is a versioned skill library, and \Lambda records node–skill bindings, parameters, and budgets. The goal is for the same program to handle variation in initial object positions, object counts, and geometry within an object category while keeping the task goal and success criterion fixed. At run time, the program may use only observations: head and wrist camera images, camera calibration, joint states, the robot model, and instruction text. Object poses, simulator state, and evaluation results are not inputs; success is determined solely by the environment’s native criterion, and the controller cannot declare success itself. On RoboDojo, we enforce this through three layers of input auditing—static code checks, interception of run-time file access, and an environment boundary that exposes only the control interface—and deploy the program as a separate policy-server process that exchanges observations and actions with the simulator only through the official client. ReSkill organizes program construction and improvement at two scales (Figure 2 ). The task level determines which stages compose a task, how stages hand off to one another, and how to recover from failure; the skill level determines whether the skill called at each stage is sufficiently reliable and improves the skill itself when it is not. Both scales use the same execution records, and revisions occur between episodes: within an evaluation, the task graph and skills remain frozen, and only the closed-loop checks within nodes retry from new observations.
