# Embodied agent-harness patterns — overview

17 main patterns grouping 58 sub-patterns (44 candidate_pattern, 14 case). 51 come from one frozen Open Scientist domain, `embodied-agent-harness/v1` (sub ids K101–K805 keep the domain's card ids; the first digit is the domain family F1–F8), built from 50 full-text readings. The other 7 (R01–R07, source `board-induced`, 2026-10-21) were induced from the wave-1 board's weak fits (60 of the first 105 assigned papers, all read in full text): R04 and R07 join the existing interface main, and R01, R02, R03, R05 and R06 each open a new main pattern. The existing mains' success conditions and failure modes keep their ids; the interface main gains two success conditions and three failure modes at the end. Every sub-pattern belongs to exactly one main. Families F1 (interface, 10 cards), F5 (offline distillation, 6), F6 (on-policy correction, 11) and F7 (RL, 8) are split by mechanism into two mains each; F2, F3, F4 and F8 are one main each. Sub-pattern cards copy the domain cards faithfully, with arXiv#signature citations; board-induced cards cite `arXiv#board`. No outcome labels exist in this build, so there are no accept rates; success conditions and failure modes are reading-derived. See also [anti-patterns](anti-patterns.md).

## The field

An **agent harness** is the loop around a frozen frontier LLM/VLM that controls a robot, a navigating agent or a simulator: what the model observes (RGB on request, depth and map queries, text descriptions), how its outputs become actions (primitive batches, semantic action units, code cells, calls to learned tools or frozen VLAs), what is checked outside the model (gates, success detectors, monitors), what is remembered (context windows, notes, skill libraries, replay cards), and how the harness itself is revised from traces. The second half of the field treats the harnessed frontier model as a **teacher** and asks how a compact VLM/VLA **student** inherits its competence — by piloting the same harness after SFT, by on-policy correction at the states it visits, or by RL inside the harness. A third strand is methodological: the harness effect is confounded with the model effect, and most papers report only end-to-end success.

Read left to right, the teacher loop is: fix the interface the model sees and acts through, put checks and stopping rules outside the model, carry context and skills across steps and episodes, then let an optimizer revise all of it from traces (the co-evolution sub-pattern K403 already alternates harness revision with student RL). The student loop is: SFT on success-filtered or privileged teacher data, then correction or distillation at states the student itself visits, then RL through (or aligned with) the deployment harness, with teacher data used to make sparse success learnable. Evaluation methodology applies to every claim on both sides. The board-induced mains sit beside this loop: three keep a frozen LLM in a different role (translator for a classical solver, multi-robot allocator, author of controller code that runs without it), one trains the planner itself instead of a student of a harness teacher, and one spends test-time compute on choosing among sampled actions.

## Sister radars

- **HarnessRSI Daily** (https://github.com/CrepuscularIRIS/HarnessRSI-Daily) tracks non-weight self-improvement: agents that rewrite their own prompts, memory, skills, tools and harness code. It overlaps with [Revise the Harness Itself from Execution Traces](main/harness_self_optimization.md) and, for experience reuse, with [Build Context, Notes and Skills with the Weights Frozen](main/harness_memory_skill_reuse.md); EH Radar keeps only the embodied and teacher-for-student side of that work.
- **CUA Radar** (https://github.com/CrepuscularIRIS/cua-architecture-radar) is the computer-use / GUI-agent radar this repository is cloned from. Its planner–grounder, structured-observation and trajectory-training patterns are the GUI counterparts of the interface and student-training mains here; GUI papers that appear in this domain (hybrid GUI + tool agents, next-screenshot privileged distillation) are read only for the mechanism they share with embodied harnesses.

## How to read the cards

- **Main card** (`patterns/main/<id>.md`): definition, operational signature, when to apply, the sub-pattern table, then **Success conditions** (S1, S2, …) and **Failure modes** (F1, F2, …) in the order they appear. Each is a bold-named property that can be checked in a paper's text, with numbers and `arXiv#signature` citations from the readings. `research/build_conditions.py` numbers them into `research/patterns/conditions.json`, and scorers judge papers against these ids, so rerun it after editing a main card. *Accepted vs rejected gap* stays `pending` until outcome labels exist. *Reviewer expectations* quote `profile/expectations.json` (E01–E22, derived from what the read papers do or concede, not from reviews). *Related anti-patterns* link to [anti-patterns.md](anti-patterns.md).
- **Sub card** (`patterns/sub/Kxxx.md`, `patterns/sub/Rxx.md`): the domain card (or, for R cards, a board-induced card in the same format) — operation, information access (who sees what: teacher/student, frozen/trained, harness kept or not), contrasts with sibling cards, transfer conditions, *When it works*, *When it fails*, counterexamples and sources with section locators. `candidate_pattern` means 2+ full-text papers share the operation; `case` means one paper.
- **Citations** are `arXiv#sN` signature ids from the domain readings (`arXiv#board` for the board-induced R cards, read from the full text during wave-1 induction); cards do not name papers in prose, and the Sources section lists titles.
- **Machine-readable views**: `research/patterns/taxonomy.json` (main → subs, sub → main/status) and `research/patterns/taxonomy_view.json` (one row per sub with its operation), used for assignment.
