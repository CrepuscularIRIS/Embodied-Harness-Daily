# K202 — Run the executor until a completion or stagnation monitor fires, then hand control back to the planner
_parent: **Gate, Monitor and Diagnose Actions Outside the Model** ([`external_verification_control`](../main/external_verification_control.md)) · status: candidate_pattern · source card: `K202-monitor-triggered-handback.md` (frozen domain `embodied-agent-harness/v1`)_

## Operation
keep the low-level executor on the current subgoal until a success detector or progress-threshold/stagnation rule fires, then let the planner advance or replan

- Information access: Planner and executor frozen (2606.10267); VLA tools trained with a progress head, planner frozen (2605.13119); 2606.10267#s1: detector queried with privileged simulator state in sim, image-only on the real robot; 2605.13119#s2: tool returns only local progress at 2 Hz; planner does not watch low-level steps.
- Contrasts: Information contrast: privileged detector (2606.10267#s1) vs executor-reported progress (2605.13119#s2).
- Transfer: Requires a completion signal the deployed system can compute; a privileged sim detector does not transfer.
- Status: candidate_pattern (2 full-text paper(s))

## When it works
- Static tabletop scenes where latency is not a factor; detector as accurate as possible (2606.10267#s1)
- Executors trained to report invocation progress (tool-aligned post-training) (2605.13119#s2)

## When it fails
- High false-positive rates collapse performance; correlated false negatives can stall a command; long fixed horizons cause timeouts (2606.10267#s1)
- Planner never trained; one robot/camera real study; planner gains depend on executor invocation fidelity (2605.13119#s2)

## Counterexamples
- A planner over a plain SFT VLA hurts on LIBERO-Long (-0.2/-11.8/-12.0) (2605.13119#s2)
