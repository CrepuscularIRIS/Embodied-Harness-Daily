# K403 — Alternate RL on the student with harness revisions accepted only when they help the current checkpoint
_parent: **Revise the Harness Itself from Execution Traces** ([`harness_self_optimization`](../main/harness_self_optimization.md)) · status: candidate_pattern · source card: `K403-gated-harness-policy-co-evolution.md` (frozen domain `embodied-agent-harness/v1`)_

## Operation
alternate blocks of RL on the student (harness frozen) with harness revisions proposed from those trajectories, accepting a revision only if it improves outcomes under the fixed current checkpoint

- Information access: Student weights trained by outcome-reward RL; proposer frozen (unstated in 2609.37105; GPT-5.6 Sol through Codex in 2610.28069#s2); Acceptance compares incumbent vs candidate with the same checkpoint and tasks; the student deploys with the evolved harness.
- Contrasts: Contrasts with K401 (model frozen) and K701 (harness fixed during RL).
- Transfer: Applies when the student will deploy with an evolvable harness and rollouts are cheap; simulator cost is the main barrier.
- Status: candidate_pattern (2 full-text paper(s))

## When it works
- Same weight and harness optimizers across schedules; checkpoint and harness picked on a separate validation set (2609.37105#s1, 2609.37105#s2)
- Cheap sandbox rollouts for candidate comparison; a trainable-rate metric from GRPO group outcome mix (2610.28069#s2)

## When it fails
- Progress not monotonic: weight stages can reduce validation score; one training run per condition; text/tool tasks only (2609.37105#s1)
- Validation reuse across rounds risks adaptive selection; strict-improvement gate on noisy point estimates; 53-58 validation tasks (2609.37105#s2)
- Acceptance is not a significance test; extra rollouts plus teacher calls; 184-rollout comparisons would be far costlier in embodied settings (2610.28069#s2)
