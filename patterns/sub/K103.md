# K103 — Model proposes a visual target; harness back-projects, checks feasibility and executes or asks to reselect
_parent: **Design the Frozen Model's Observation and Action Interface** ([`observe_act_interface`](../main/observe_act_interface.md)) · status: candidate_pattern · source card: `K103-target-proposal-geometric-execution.md` (frozen domain `embodied-agent-harness/v1`)_

## Operation
let the model pick a pixel or editable target pose, have the harness back-project/solve IK and plan, check feasibility, and return execute or reselect/revise feedback

- Information access: Frozen VLM; nothing trained; Tool (not the model) holds metric depth, intrinsics/extrinsics, robot geometry, IK and motion planner; model sees RGB views (plus BEV map or multi-view Canvas) and feasibility feedback.
- Contrasts: Contrasts with K201 (the check here is geometric feasibility of the model's own target, not a rule gate on arbitrary proposals).
- Transfer: Requires depth the tool can back-project metrically; targets beyond reliable depth range are untested.
- Status: candidate_pattern (2 full-text paper(s))

## When it works
- Metric RGB-D or a base-frame point cloud plus calibration available to the tool (2606.10577#s1, 2609.29964#s1)
- A local planner (TEB / SCAN-Planner, cuRobo) executes validated targets (2606.10577#s1, 2609.29964#s1)

## When it fails
- Targets restricted to visible pixels with valid depth; single run, 100 episodes, no variance (2606.10577#s1)
- No per-component ablation (contact views vs rehearsal vs drag correction); failures from cross-view grasp misjudgment, losing object identity, premature completion; bounded by the backbone's multi-view integration (2609.29964#s1)
