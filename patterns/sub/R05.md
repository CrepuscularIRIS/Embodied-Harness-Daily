# R05 — Write the controller as code and rewrite it between trials from execution diagnostics
_parent: **Write the Policy as Code and Rewrite It from Trial Diagnostics** ([`code_policy_trial_revision`](../main/code_policy_trial_revision.md)) · status: candidate_pattern · source: board-induced 2026-10-21 (wave-1 weak fits)_

## Operation
have a frozen LLM or coding agent write the whole controller as a program over perception, geometry and motion primitives (one program per robot or task), run it for one or more trials in simulation, diagnose the failures from execution logs, phase outcomes, key frames or a VLM's reading of rollout images or video, and rewrite the program, repeating until it succeeds or a budget runs out; the deployed artifact is the program, with no model in the control loop at run time

- Information access: Frozen models in all members; the writer sees the primitive API, its own previous code and trial diagnostics; one variant has the coding agent read 256x256 RGB-D key frames and structured outcomes with no ground-truth object poses in the controller (2603.04466#board); one fuses symbolic simulator logs with a VLM's judgement of checkpoint images from the most informative failed run (2508.02629#board); one adds constraint review, static checks and a VLM critique of simulation video before auto-deploying code to a robot swarm (2503.23875#board).
- Contrasts: Contrasts with K105 (code cells composed and executed inside one episode while the planner stays in the loop; here code is rewritten between episodes and runs without the model) and K401 (an optimizer revises the harness around a frozen agent model; here the revised program is the policy itself). Contrasts with K503 (a privileged program teacher whose successes become demonstrations for a student; here the program is the deliverable). Contrasts with K203 (the agent writes a separate diagnostic probe program; here diagnosis is read from logs and images).
- Transfer: Code-as-policies plus iterative program repair; transfers when trials are cheap and resettable (simulation) and the primitive library covers the task; real-robot rewriting and held-out evaluation are untested.
- Status: candidate_pattern (3 member papers, all with full text)

## When it works
- Rewriting from trial evidence is compared with one-shot code on the same tasks: average success 47.4% (one-shot code) -> 60.4% (execution feedback) -> 63.9% (adding VLM diagnosis) on one benchmark and 62.1 -> 66.7 -> 71.3 on another (2508.02629#board)
- The rewrite history shows which fixes mattered: a stacking controller goes 0% (v0-v6) -> 33% after a back-projection sign fix -> 91% at v20; lift and pick-place reach 100% within 3 and 2 rewrites, with 20/20 repeats on pick-place (2603.04466#board)
- Code is checked before and after simulation and deployed automatically: 81% mean success over 10 tasks x 100 trials, and 74% vs 37-40% for three code-generation baselines on 6 tasks (2503.23875#board)

## When it fails
- Rewriting and scoring use the same task instances, with no held-out split; the trial counts behind the 91% are not stated; 3 simulated tasks only (2603.04466#board)
- Baselines are missing or weaker than the classical controller: one study has no baseline at all, and in another hand-tuned flocking and assignment controllers score higher on average than the generated code (2603.04466#board, 2503.23875#board)
- Convergence claims mix incomparable settings: the headline iteration reduction (2.42 -> 1.76) compares two benchmarks run with different planners; tasks whose skill is missing from the library stay at 0% (2508.02629#board)
- Perception is emulated or simulated: swarm robots get positions from an indoor positioning system rather than onboard sensing; no member rewrites code on a real robot from real failures (2503.23875#board, 2508.02629#board)

## Counterexamples
- The VLM part of the diagnosis adds little: 74% with the video critique vs 71% without it; 60.4 -> 63.9 from adding visual diagnosis to execution feedback, and per-task success drops on some tasks (handover 50 -> 27, a stacking task 68 -> 64) (2503.23875#board, 2508.02629#board)
- The loop does not carry a weaker agent: a second coding agent with the same budget solved none of the three tasks, so the gain belongs to the agent as much as to the loop (2603.04466#board)
