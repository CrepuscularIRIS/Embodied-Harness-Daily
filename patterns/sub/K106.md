# K106 — Train a compact policy to be invoked by a planner through a typed call
_parent: **Let a Frontier Planner Compose Code, Learned Tools and Frozen VLAs** ([`planner_composes_code_and_policies`](../main/planner_composes_code_and_policies.md)) · status: candidate_pattern · source card: `K106-learned-policy-as-typed-tool.md` (frozen domain `embodied-agent-harness/v1`)_

## Operation
train a compact policy whose input is a typed planner call (tool family + local instruction, or a JSON command) and expose it as a callable tool for multi-step motion

- Information access: The tool policy is trained (LoRA adapters per tool family on a VLA; Qwen3-VL-4B waypoint policy); the planner stays frozen; The tool sees only robot observations, the call and short history; not the planner's maps or LiDAR.
- Contrasts: Contrasts with K107 (frozen VLA steered without training).
- Transfer: Requires that the planner's calls fall within the tool's training distribution; a compact student can take the tool's place, i.e. part of the harness is internalized into a tool.
- Status: candidate_pattern (2 full-text paper(s))

## When it works
- Demonstrations can be segmented into invocation windows with a data-derived tool taxonomy (2605.13119#s1)
- The tool's value depends on the coding backend that calls it (2609.39207#s2)

## When it fails
- Invocation-aligned post-training first reduced pi0.5 (93.4 -> 91.2); primitives absent from data need new demos; progress target is a temporal proxy (2605.13119#s1)
- Trained for atomic behaviours, not global exploration; object search needs a separate planner (2609.39207#s2)

## Counterexamples
- Benefit is small or negative for the strongest backend (Astra RxR SR drops) (2609.39207#s2)
